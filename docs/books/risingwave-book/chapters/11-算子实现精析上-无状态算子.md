## 11.1 无状态 vs 有状态

在正式开始之前，先明确一个分类标准：**算子是否持有需要在 Barrier 之间持久化的状态表？**

- **无状态算子**：每条 Chunk 独立计算，不依赖历史数据。Filter、Project、Union 属于这一类。
- **有状态算子**：需要维护跨 Barrier 的状态表（通常在 Hummock 中）。HashJoin、HashAgg、Materialize 属于这一类。

无状态算子的实现普遍比有状态算子简单一个数量级，但它们占据了 Actor 中大部分的算子节点。深入理解它们，才能理解一条数据在 Actor 内部经历了什么。

> **第一性原理思考**：一个算子是"无状态"的，是否意味着它不涉及状态？并非如此。Filter 的 Upsert 模式需要知道上一次过滤结果，Chain 需要追踪 Backfill 进度，Source 需要管理 Split 分配。真正的区别在于：状态是否需要**跨 Barrier 持久化**。Upsert Filter 的状态在一次 Chunk 内即消费即弃，Chain 的进度信息放内存里足以。这就是"无持久状态"和"有持久状态"的边界。

## 11.2 SourceExecutor——数据的源头

`SourceExecutor`（`source/source_executor.rs:63-85`）是每个 Source Fragment 的根算子：

```rust
pub struct SourceExecutor<S: StateStore> {
    actor_ctx: ActorContextRef,
    stream_source_core: StreamSourceCore<S>,
    metrics: Arc<StreamingMetrics>,
    barrier_receiver: Option<UnboundedReceiver<Barrier>>,
    system_params: SystemParamsReaderRef,
    rate_limit_rps: Option<u32>,
    is_shared_non_cdc: bool,
    barrier_manager: LocalBarrierManager,
}
```

### 11.2.1 Split 分配与 Source Reader

SourceExecutor 的核心是 `StreamSourceCore`——它封装了连接器特定的 SourceReader。当 Actor 启动时，第一个 Barrier 携带 `SplitAssignments`（通过 `Add` 或 `Update` Mutation 的 `actor_splits` 字段），告诉 SourceExecutor 它负责哪些 Split（Kafka Partition、PostgreSQL 表分片等）。

关键方法 `barrier_to_message_stream`（`source/mod.rs`）检查 Barrier 中是否有 Split 变更：
- `Mutation::SourceChangeSplit` → 更新 `StreamSourceCore` 的 Split 集合
- `Mutation::Throttle` → 应用限流配置
- `Mutation::Pause` / `Mutation::Resume` → 控制 SourceReader 的读写状态

### 11.2.2 共享 Source 优化

`is_shared_non_cdc` 标识一个重要的优化：当多个下游 MV 共享同一个 Source 时，SourceExecutor 只运行一次，通过 `DispatchExecutor` 将数据广播给所有下游。这避免了重复消费外部数据源（如 Kafka）的开销。

### 11.2.3 执行循环

SourceExecutor 的 `execute` 内部是一个复杂的流组合：

```
barrier_receiver → 检查 Barrier（Split 变更 / Pause / Resume）
                     │
stream_reader     → 从外部连接器读取 StreamChunk
                     │
           两者通过 futures::stream::select 合并
                     │
              Watermark 生成逻辑
                     │
              下游 Executor 链
```

## 11.3 ChainExecutor——快照与增量的合流

`ChainExecutor`（`chain.rs`）实现了一个关键的流模式：**先消费历史快照，再切到增量消费**。

```
          Snapshot Reader           Upstream Executor
         (读取全部存量数据)          (读取增量 changelog)
                │                          │
                └──────────┬───────────────┘
                           │
                      ChainExecutor
                           │
                     下游算子
```

ChainExecutor 的逻辑可以概括为：
1. **启动时**：检查 Barrier 是否是 `is_newly_added(actor_id)`——如果是新创建的 Actor，需要先输出历史数据
2. **Snapshot 阶段**：从 `BatchTable` 读取全部存量行 → 包装为 `StreamChunk(Insert)` 输出
3. **对齐阶段**：等待 Snapshot 完成 + Upstream 的第一个 Barrier
4. **增量阶段**：切换为只消费 Upstream Executor 的 changelog，不再读 Snapshot

这个设计的精妙之处在于：ChainExecutor 保证了**存量数据和增量数据的分界线是一个明确的 Barrier**。在 Barrier 之前，下游算子消费到的是全量 Snapshot（可能包含多批 `Insert`）；Barrier 之后，消费到的是增量 changelog。这个分界线是可恢复的——Checkpoint 后重启时，Barrier 所在 epoch 之后的数据从 Snapshot 恢复，之前的数据从 changelog 继续。

## 11.4 FilterExecutor——行的筛选

`FilterExecutor`（`filter.rs:37-44`）是最纯粹的算子——它接收一个 chunk，对每一行计算布尔表达式，保留结果为 true 的行。

```rust
pub struct FilterExecutorInner<const UPSERT: bool> {
    _ctx: ActorContextRef,
    input: Executor,
    expr: NonStrictExpression,
}
pub type FilterExecutor = FilterExecutorInner<false>;
pub type UpsertFilterExecutor = FilterExecutorInner<true>;
```

通过 const generic `UPSERT: bool`，同一个 struct 支持两种模式。

### 11.4.1 标准模式

标准模式（`filter.rs:107-143`）用 visibility bitmap 来做过滤。

对于 `Insert` / `Delete`（单行操作），直接将 filter 结果设置为 visibility。filter 返回 false 的行被标记为不可见。

对于 `UpdateDelete + UpdateInsert`（成对更新），需要根据前后两行的 filter 结果来决定输出：
- `(true → false)`：输出 `Delete`（旧行可见，新行不可见 → 删除）
- `(false → true)`：输出 `UpdateDelete + Insert`（旧行不可见，新行可见 → 插入）
- `(true → true)`：输出 `UpdateDelete + UpdateInsert`（都可见 → 保持更新语义）
- `(false → false)`：输出 `UpdateDelete + UpdateInsert`，但两行都标记为不可见

这四种情况完整覆盖了更新操作在过滤后的语义，正确性依赖于 visibility bitmap 的精确控制。

### 11.4.2 Upsert 模式

Upsert 模式（`filter.rs:82-106`）的语义不同：它总是输出 `Insert` 或 `Delete`，不输出 `Update`。

```
当一个 Insert 行 filter 为 true → 保留 Insert
当一个 Insert 行 filter 为 false → 输出 Delete（可能是 no-op）
当一个 Delete 行不论 filter 结果 → 始终输出 Delete
```

为什么有这种需求？因为 Upsert 语义下，同 Primary Key 的行会覆盖旧值。如果 filter 条件变了（比如列值更新后不再满足 filter），需要发出一个 Delete 来清除已物化的旧行，而不能依赖"上一个版本"的信息（因为 Upsert 本身就丢弃了旧版本）。

### 11.4.3 执行方法

```rust
// filter.rs:173-195
async fn execute_inner(self) {
    let input = self.input.execute();
    for msg in input {
        let msg = msg?;
        match msg {
            Message::Watermark(w) => yield Message::Watermark(w),
            Message::Chunk(chunk) => {
                let pred_output = self.expr.eval_infallible(chunk.data_chunk()).await;
                match Self::filter(chunk, pred_output)? {
                    Some(new_chunk) => yield Message::Chunk(new_chunk),
                    None => continue,  // 全部过滤，不产出
                }
            }
            m => yield m,  // Barrier 直接透传
        }
    }
}
```

Watermark 无条件透传，Barrier（`m => yield m`）也是无条件透传。Filter 只关心 Chunk。

## 11.5 ProjectExecutor——列的裁切与计算

`ProjectExecutor`（`project/`）有两种变体：

1. **简单 Project**：只做列的选择和重排（`select $0, $2`），输出列是输入列的子集，无表达式计算
2. **表达式 Project（ProjectSet）**：对输入列应用表达式计算产生新列（`SELECT upper(name), age+1`），输出列可能和输入列完全不同

ProjectExecutor 也透传 Barrier 和 Watermark——但它需要做 `Watermark::transform_with_indices`（`mod.rs:1244-1249`）来重新映射 Watermark 的列索引。

## 11.6 UnionExecutor——多路合并

`UnionExecutor`（`union.rs`）将多个 Executor 的产出合并为一条流：

```
    Input A ──┐
              │
    Input B ──┼── UnionExecutor ──► 下游
              │
    Input C ──┘
```

Union 的内部使用 `DynamicReceivers` 做屏障对齐（与 `MergeExecutor` 逻辑相同），但它做了一件额外的事：**合并后的流需要保证屏障的 epoch 保持递增**。因为多个输入可能来自不同的 Fragment，它们各自以不同的速度到达 Barrier，Union 确保输出给下游的是一个 epoch 严格递增的消息流。

UnionExecutor 常用于 `UNION ALL` 查询场景——两个子查询的结果合并为一条流。它也用于某些优化器的重写路径。

## 11.7 ExpandExecutor——行展开

`ExpandExecutor`（`expand.rs`）是一个一进多出的变换：一行输入扩展为多行输出。

典型的使用场景是 **GROUPING SETS**：

```sql
SELECT region, city, SUM(amount)
FROM orders
GROUP BY GROUPING SETS ((region, city), (region), ())
```

在生成聚合计划时，Optimizer 将一个 `Expand` 节点插入在 Agg 之前，将每行复制多次（每行对应一个 grouping set），用特殊的列标记区分哪些 grouping set 中哪些列为 NULL。Agg 算子根据这些标记做正确的聚合。

Expand 同样透传 Barrier 和 Watermark——每一条 Barrier 对应展开后的多条 Barrier（但 Barrier 在流系统中需要合并，所以 Expand 输出的 Barrier 流保持不变：一条 Barrier 进，一条 Barrier 出）。

---

## 11.8 WatermarkFilterExecutor——水平线裁剪

`WatermarkFilterExecutor`（`watermark_filter.rs`）的实现很简单但意义重大。

当 Hop 窗口或 Temporal Join 只关心最近一段时间的窗口时，WatermarkFilter 检查收到的 Watermark 值，如果 watermark 表示"这个时间之前的数据不再需要"，则丢弃它对应的数据 Chunk。这和后端的 State Cleanup Strategy 配合使用，防止状态表无限增长。

对于 Upsert 流，`UpsertWatermarkFilterExecutor` 在收到 Watermark 后还会发出额外的 Delete 记录，清除已物化的过期数据。

## 11.9 HopWindowExecutor——窗口时间戳计算

`HopWindowExecutor`（`hop_window.rs`）用于 Hop 窗口：

```sql
SELECT window_start, window_end, SUM(amount)
FROM orders
GROUP BY HOP(event_time, INTERVAL '1' MINUTE, INTERVAL '1' HOUR)
```

Hop 窗口的语义是：每个事件落在多个窗口内（按 slide/step 滑动）。如果 slide = 1 分钟，window_size = 1 小时，每行数据需要被复制到 60 个窗口中。

`HopWindowExecutor` 做的核心计算：**对每行数据，计算它所属的所有窗口的 `window_start` 和 `window_end`，然后展开为多行**。输出中会新增两列（或替换事件时间列）：`window_start` 和 `window_end`。

与 `ExpandExecutor` 不同，HopWindow 的展开是基于时间计算的（窗口大小和滑动步长），而 Expand 是基于 grouping set 的组合数。

HopWindow 的关键计算可以概括为：

```
对于输入行 (event_time=12:05:30):
  slide = 1 min, window_size = 1 hour

  窗口 1: window_start=11:06, window_end=12:06
  窗口 2: window_start=11:07, window_end=12:07
  ...
  窗口 60: window_start=12:05, window_end=13:05

输出 60 行，每行用对应的 window_start 替换 event_time 列
```

## 11.10 RowMergeExecutor——多流合并去重

`RowMergeExecutor`（`row_merge.rs`）用于 Sink into Table 场景。当 `ALTER TABLE sink_into_table` 时，原来写入老 Sink Fragment 的数据和写入新 Sink Fragment 的数据需要合并去重。

其核心逻辑：
1. 从多个上游接收 `StreamChunk`
2. 按 Primary Key 合并行——如果同一个 Key 在多个上游中都出现，保留最新版本
3. 输出合并去重后的 Chunk

它是有状态的（需要内存中维护 Key 的去重映射），但不跨 Barrier 持久化。

## 11.11 无状态算子的共同模式

回顾以上所有算子，它们共享一个通用的流处理模式：

```
async fn execute_inner(self) {
    let input = self.input.execute();     // ① 获取上游消息流
    for msg in input {                    // ② 逐条消费消息
        let msg = msg?;
        match msg {
            Message::Chunk(chunk) => {
                // ③ 处理数据，变换为新 Chunk
                yield Message::Chunk(transform(chunk));
            }
            Message::Watermark(w) => {
                // ④ 透传或变换 Watermark
                yield Message::Watermark(w);
            }
            m => yield m,                 // ⑤ Barrier 无条件透传
        }
    }
}
```

这个模式的本质是：
1. **Chunk 是算子关注的核心**——每个算子只变换 Chunk
2. **Watermark 需要维护列索引的一致性**——通过 `transform_with_indices` 或 `transform_with_expr`
3. **Barrier 是无条件透传的**——无状态算子不需要在 Barrier 时做状态合并

在 RisingWave 中，这种模式被 `#[try_stream]` 宏反复使用，形成了算子的 "trait implementation factory"——几乎所有无状态算子的 `Execute` impl 都遵循这个模板。

## 11.12 小结

本章覆盖了 RisingWave 流计算引擎中的所有主要无状态算子：

- **SourceExecutor**：外部数据接入，Split 分配，共享 Source 优化
- **ChainExecutor**：快照读取 + 增量消费的 Barrier 分界线
- **FilterExecutor**：标准模式和 Upsert 模式两套过滤语义，Update 操作的四状态变换
- **ProjectExecutor**：列裁切与表达式投影，Watermark 列索引重映射
- **UnionExecutor**：多路合并与 epoch 一致性保证
- **ExpandExecutor**：GROUPING SETS 的行展开
- **WatermarkFilterExecutor**：基于 Watermark 的数据裁剪和过期清除
- **HopWindowExecutor**：基于 slide 和 window_size 的窗口时间展开
- **RowMergeExecutor**：Sink into Table 的多流去重合并

无状态算子的实现模式高度一致：**Chunk 变换 + Watermark 维护 + Barrier 透传**。这个三件套是理解 RisingWave 流计算引擎的基石。

从下一章开始，我们将进入有状态算子的世界——HashJoin、DeltaJoin、TemporalJoin 等连接算子，看它们如何在状态表中维护跨 Barrier 的数据关联。
