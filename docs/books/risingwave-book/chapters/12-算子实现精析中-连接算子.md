## 12.1 Join 在流和批中的本质区别

批处理中，Hash Join 的流程是：Build 右表 Hash Table → 扫描左表 → Probe 匹配 → 输出结果。所有数据都在内存里，用完就丢。

流处理中，这个逻辑完全不成立。左表和右表的数据是**随时间增量到达的**，你不可能等"所有数据到齐"再做 Build。这意味着：

1. **两侧都需要维护 Builder**：左表数据来自左边的流，右边来自右边的流。任何一侧有新数据到达时，都需要去另一侧的状态表中 Probe
2. **状态需要持久化**：状态表（JoinHashMap）不能只在内存里——Actor 崩溃恢复后必须能从 Storage 重建
3. **更新和删除需要追踪匹配数量**：Hash Join 中，一行左表数据可能匹配右表的多行。如果左表的一行被删除了，必须知道它之前匹配了多少行右表数据，才能发出正确数量的 Delete

> **第一性原理思考**：Hash Join 的状态表本质上是一个 **Multi-Map**——一个 key 对应多个 value。批处理中这是内存结构（Python dict of lists），但流处理中这必须是**可持久化的、可增量更新的、支持并发读写的存储结构**。这就是 Hummock State Table 在 Join 场景中的角色。JoinHashMap 不是简单的 HashMap，而是在 Hummock 之上的一个精心设计的抽象层。

## 12.2 JoinSide——一侧的状态

```rust
// hash_join.rs:91-119
struct JoinSide<K: HashKey, S: StateStore, E: JoinEncoding> {
    ht: JoinHashMap<K, S, E>,           // 核心：连接哈希表
    join_key_indices: Vec<usize>,       // 连接键在原始行中的列位置
    all_data_types: Vec<DataType>,      // 所有列（不含 degree）的数据类型
    start_pos: usize,                   // 这一侧在输出中的起始列位置
    i2o_mapping: Vec<(usize, usize)>,   // 输入列 → 输出列的映射
    input2inequality_index: Vec<Vec<(usize, bool)>>, // 非等值条件的列映射
    non_null_fields: Vec<usize>,        // 非等值条件要求非 NULL 的列
    state_clean_columns: Vec<(usize, usize)>, // 可根据 Watermark 清理的列
    need_degree_table: bool,            // 是否需要 Degree 表
}
```

两侧各维护一个 `JoinSide`，记录各自的数据和元数据。

### 12.2.1 JoinHashMap——可持久化的 Multi-Map

`JoinHashMap` 不是一个普通的 `HashMap<K, Vec<V>>`。它基于 Hummock State Table 实现，使用**编码格式**（`JoinEncoding`）将多行数据序列化到存储中。

核心设计要素：
- **Entry State**：存储 join key → 对应的所有行。用 encoding 格式打包多行为一个 blob，减少 key 数量
- **缓存层**：`JoinHashMap` 维护 in-memory cache，近期访问的 key 不重新读存储。缓存由 `join_cache_evict_interval_rows` 控制逐出频率
- **Dirty 标识**：当缓存被修改但未 flush 时标记为 dirty。Barrier 时 flush 到 State Table。`is_dirty()` 检查是否安全清缓存

### 12.2.2 Degree 表

`need_degree_table` 标识需要 **Degree 表**的场景。Degree 表追踪"一个 join key 下的某一行被另一方匹配了多少次"。

```
例如：左表 (user_id=1, 'Alice') 匹配右表的两行
  (user_id=1, 'order_001') 和 (user_id=1, 'order_002')

Degree 表记录：
  key=(left, 1, row_Alice) → degree=2

如果右表的 order_001 被删除：
  degree 从 2 降为 1 → 只需输出 1 个 UpdateDelete（修改行）
  degree 如果是 1 → 降为 0 → 输出 1 个 Delete

如果左表的 Alice 被删除：
  degree=2 → 输出 2 个 Delete（对应匹配的两个订单）
```

Degree 表在 Retract 流（非 Append Only）中是**必需的**——没有它，你就无法知道删除一行需要输出多少条记录。

## 12.3 HashJoinExecutor 的类型参数矩阵

```rust
// hash_join.rs:157-204
pub struct HashJoinExecutor<K: HashKey, S: StateStore,
    const T: JoinTypePrimitive, E: JoinEncoding>
```

三个泛型参数（加一个 state store）定义了 Join 的所有变体：

| 参数 | 取值 | 含义 |
|------|------|------|
| `T: JoinTypePrimitive` | Inner / LeftOuter / RightOuter / FullOuter / Semi / Anti | Join 类型 |
| `K: HashKey` | 由 Key 生成逻辑决定 | 连接键的 Hash 表示 |
| `E: JoinEncoding` | `CpuEncoding` / `MemoryEncoding` | 状态存储的编码格式 |

**编码格式**的选择是一个性能权衡：
- `CpuEncoding`：CPU 密集型的编解码，内存占用较小，适合数据量大的场景
- `MemoryEncoding`：空间换时间，快速存取，适合小数据量高频访问

两者都实现了 `JoinEncoding` trait，提供 `encode`/`decode`/`estimated_size` 等方法。Automatic fallback 逻辑根据 `entry_state_max_rows`（一个 key 下的最大行数）选择编码方案。

### 12.3.1 JoinType 的流式语义

不同 Join 类型在流中的行为有微妙差异：

| Join 类型 | 左新行 | 右新行 | 左删除 | 右删除 | 特殊逻辑 |
|-----------|-------|-------|-------|-------|---------|
| Inner | Probe 右表，输出匹配 | Probe 左表，输出匹配 | 输出匹配的 Delete | 输出匹配的 Delete | — |
| LeftOuter | Probe 右表，匹配则输出，不匹配也输出 NULL 行 | 只更新已有匹配 | 输出 Delete + 可能的非 NULL→NULL 更新 | 收回匹配，可能补 NULL 行 | 需要 tracking null rows |
| FullOuter | 同 LeftOuter | 同 LeftOuter（对称） | 同上 | 同上 | 两侧都要 tracking |
| Semi | Probe 右表，有匹配即输出 | 不影响输出 | 输出前一行的 Delete | 不输出（Semi 不关心右侧删除） | — |
| Anti | 同 Semi 反向 | 同 Semi 反向 | 同 Semi 反向 | 当右表新行匹配左表时收回之前输出的 Anti 匹配 | — |

## 12.4 执行流程——增量式 Join

HashJoinExecutor 的 `into_stream` 方法（~`hash_join.rs:386`附近）生成了一个复杂的 async stream。

### 12.4.1 左右交替执行

核心执行模式是：**在左右两个输入流之间交替消费，每侧消费到 Barrier 就切到另一侧**：

```
loop {
    // 消费左侧直到 Barrier
    while let msg = input_l.next() {
        match msg {
            Chunk → eq_join(chunk, is_left=true)
            Barrier → break
        }
    }
    // 消费右侧直到 Barrier
    while let msg = input_r.next() {
        match msg {
            Chunk → eq_join(chunk, is_left=false)
            Barrier → break
        }
    }
    // 两侧 Barrier 都到达 → flush state + yield barrier
}
```

这个左右交替的设计是因为**流式 Hash Join 不需要等两侧 Barrier 完全对齐才处理数据**。左表的新 Chunk 可以立即去右表 Probe——即使右表还没收到 Barrier。两个 Barrier 到达后才做 flush（将状态变更提交到 State Table）。

### 12.4.2 eq_join——增量匹配的核心

`eq_join` 方法处理一侧新到达的 Chunk：

```
对于左侧新到达的 Chunk 中的每一行:
  ① 计算 join key = hash(left_join_key)
  ② 去右表的 JoinHashMap 中查找 join key
  ③ 如果有匹配:
     - Inner Join → 输出 Join 结果行（Insert/Delete 对应输入行的 op）
     - 更新右表 Degree 表中匹配行的 degree
  ④ 更新左表的 JoinHashMap:
     - Insert 行 → 插入
     - Delete 行 → 删除
     - Update 行 → 先删后插
```

非等值条件（`cond`）在 Hash 匹配后进行二次过滤。`inequality_pairs` 处理 `t1.time > t2.time - INTERVAL '1' HOUR` 这类范围条件。

### 12.4.3 Watermark 处理与 State 清理

HashJoin 收到 Watermark 后做两件事：

1. **生成输出 Watermark**：对于 inequality 条件，取两侧 watermark 的较小值，指示"这个时间之前的数据已完整"
2. **State 清理**：根据 `state_clean_columns` 判断哪些列的 watermark 已过时而状态可清理——旧的 join key 条目可被安全删除，避免 JoinHashMap 无限增长

这需要接入 `BufferedWatermarks` 来对齐多个上游列的 watermark。

## 12.5 Delta Join——共享状态的优化

Delta Join 是 RisingWave 的一个流式特有优化。

### 12.5.1 问题场景

假设三个 MV：

```sql
CREATE MV mv1 AS SELECT * FROM t1 JOIN t2 ON t1.k = t2.k;
CREATE MV mv2 AS SELECT * FROM t1 JOIN t3 ON t1.k = t3.k;
CREATE MV mv3 AS SELECT * FROM t2 JOIN t3 ON t2.k = t3.k;
```

标准实现下，每个 MV 各自维护 t1/t2/t3 的 JoinHashMap——t1 的状态被复制了两次（mv1 和 mv2 各一份）。当 source 很多时，存储放大很严重。

### 12.5.2 Delta Join 的思路

Delta Join 将 Join 重写为**去中心化的查找模式**：

```
传统 Hash Join:
  t1: 维护 t1 的全部状态（在 mv1 和 mv2 中各一份）
  t2: 维护 t2 的全部状态

Delta Join:
  t1 → 不需要单独维护状态，t1 的变更直接去 t1 的 Arrangement（主索引）中 lookup
  t2 → 同上
  t3 → 同上
```

每个表只在自己的 MV 或主索引中维护一份状态，其他 Join 通过 **Lookup** 来引用，而不是各自复制一份。

### 12.5.3 Delta Join 的算子映射

Delta Join 在流物理计划中表现为 `DeltaIndexJoin` 节点：

```
StreamDeltaIndexJoin
├── 左输入：来自一个 stream 的增量
├── 右输入：来自另一个 stream 的增量
├── 左 Lookup → 左表的主 Arrangement（索引）
└── 右 Lookup → 右表的主 Arrangement（索引）
```

执行时，一侧的增量到达后：
1. 从本地维护的状态（Arrangement）中 lookup 已有数据
2. 从另一侧的状态中 lookup 匹配数据
3. 组合输出

Delta Join 需要 Optimizer 的 `IndexDeltaJoinRule` 来触发，需要满足：多个 Join 共享相同的连接键和分布键。

## 12.6 TemporalJoinExecutor——基于版本的时间对齐

`TemporalJoinExecutor`（`temporal_join.rs`）实现了一个特殊的连接语义：左表的一个行匹配右表中**在时间上最近（不晚于左行时间戳）的版本**。

```sql
-- 典型场景：订单关联当时的最新汇率
SELECT o.*, r.rate
FROM orders o
JOIN rates FOR SYSTEM_TIME AS OF o.order_time r
  ON o.currency = r.currency
```

实现逻辑：

```
当左表新到达一行 (currency='USD', amount=100, order_time='12:05'):
  ① 去右表（rates）找 currency='USD' 且 version <= '12:05' 的最新版本
  ② Hummock 的 time travel 特性支持按版本（epoch）查询
  ③ 取到 rate=7.24 → 输出 (USD, 100, 12:05, 7.24)
```

Temporal Join 的状态维护在右表侧：`VersionedStateTable` 记录每个 key 在不同 epoch（版本）的值。左表不需要状态——它只做 lookup。

## 12.7 AsOfJoinExecutor——快照精确连接

`AsOfJoinExecutor`（`join/asof_join.rs`）类似于 Temporal Join 但用于批式快照场景。支持两种编码：
- `AsOfCpuEncoding`：CPU 密集的编码/解码
- `AsOfMemoryEncoding`：内存优化的编码

AsOf Join 常用于 Backfill 场景——在 Backfill 期间需要对齐"快照时点"的版本，而不是"当前最新"版本。

## 12.8 LookupJoinExecutor——维表查询

`LookupJoinExecutor`（`lookup.rs`）实现的是**维表 Join**（或称为 Lookup Join）：

```
左表（事实表流）→ 对每一行 → Lookup(右表 State Table) → 输出匹配结果
```

与 Hash Join 的区别：
- Lookup Join **只在一侧维护状态**（右表=维表），左表只做 lookup
- 维表相对静态，Lookup 的开销远小于两侧同时 Build Hash Table
- 不需要 Degree 表（维表的行不会被频繁删除）

Lookup Join 有两种数据来源：
1. **`LookupExecutor`**：从 State Table 查找（内存 + Hummock）
2. **`LookupUnionExecutor`**：合并多个 lookup 源，取最新版本

---

## 12.9 NestedLoopTemporalJoinExecutor——宽表展开

`NestedLoopTemporalJoinExecutor`（`nested_loop_temporal_join.rs`）是效率最低但最通用的连接方式：对左表的一批行，遍历右表的全部匹配范围。典型的 Nested Loop 复杂度 O(N*M)，只在**维表小且缺少合适索引**时使用。

## 12.10 Join 算子的 Watermark 传播

连接算子的一个独特挑战是 **Watermark 如何通过 Join**。

对于等值 Join（Hash Join），如果连接键就是 Watermark 列（如 `t1.event_time = t2.event_time`），则输出 Watermark 可以取两侧的最小值：

```
左侧 Watermark(event_time) = 12:30
右侧 Watermark(event_time) = 12:25
→ 输出 Watermark = min(12:30, 12:25) = 12:25
```

这是安全的，因为 12:25 之前两侧的数据都已被消费和处理，Join 结果保证完整。

对于不等式条件（如 `t1.time > t2.time - INTERVAL '1' HOUR`），Watermark 传播更复杂——需要计算在不等式约束下的最小保证值。

## 12.11 小结

本章深入了 RisingWave 中五类连接算子的实现原理：

- **HashJoinExecutor**：两侧 Build + Probe，JoinHashMap 可持久化 Multi-Map，Degree 表追踪匹配数量，CpuEncoding/MemoryEncoding 可选编码
- **Delta Join**：通过 Arrangement Lookup 共享状态，避免多个 MV 重复存储同一表的状态
- **TemporalJoinExecutor**：基于版本（epoch）的时间对齐连接
- **AsOfJoinExecutor**：快照精确连接，用于 Backfill 场景
- **LookupJoinExecutor / NestedLoopTemporalJoinExecutor**：维表 Join 的两种模式

连接算子的核心复杂度来自**需要同时管理两侧的状态** + **更新的匹配计数** + **Watermark 在不等式条件下的传播**。这些机制共同保证了流式 Join 在正确性和性能之间的平衡。
