# Highway-01｜先定义正确结果，再选择向量宽度

预算：15–20分钟。前置：C++数组、整数类型、简单循环。本课新增：lane数量与
字节宽度的区别，以及一个可以作为后续向量实现oracle的标量契约。
这是学习内容，不是Highway新增功能的报道。

## 工程问题

列式扫描常做两件事：筛出满足谓词的值，再把这些值累加。
假设输入`[-3, 4, 0, 9, -1]`，条件为严格大于0，正确输出总和是13。
以后无论一次处理4个、8个还是更多元素，都应在约定输入范围内得到同样的整数结果。
向量宽度可以改变执行方式，不能改变这个语义。

首期输入类型为`int32_t`，元素数`n <= 1,000,000`，阈值也是`int32_t`，
总和为`int64_t`。空输入返回0，等于阈值的元素不计入。
输入在调用期间有效且只读。本课只做求和；后续过滤输出还要额外约定容量、稳定顺序与别名。

为什么限制输入数？一个`int32_t`绝对值最多为`2^31`，一百万个这样的值的绝对和上界
是`2.147483648e15`，仍小于`int64_t`正数上限。这个证明只保护64位累加过程，
不保护先在32位lane中完成的加法。因此我们先把每个参与累加的值转换到64位。
如果取消长度上限，必须重新选择溢出策略或结果类型，不能默认oracle永远可靠。

## lane、向量与指针到底分别计什么

lane是向量里的一个逻辑元素。固定256位向量若使用32位元素，通常容纳8个元素；
换成64位元素则只有4个。这里有三个不同数量：一个元素的字节数、一次操作的lane数、
整个数组的元素数。把它们混用，循环步进与边界判断都会错。

例如指针`p`的类型是`int32_t*`，`p + 8`前进的是8个元素，也就是32字节。
如果把32字节宽度当成元素步进写成`p + 32`，会跳过24个待处理元素。
如果把lane数硬编码成8，迁移到另一目标后又可能在读取范围或索引覆盖上出错。
这些错误与「算术指令是否快」无关，发生在我们选择了错误的执行单位时。

Highway用tag描述lane类型与向量形态，再通过`Lanes(d)`取得当前tag的lane数。
`ScalableTag<T>`用于表达目标允许的向量形态；它不是承诺每台机器都有同样字节宽度。
代码应围绕实际lane数组织块，不把一台AVX2机器上的8个lane写成跨平台常量。
也不能把`Lanes(d)`一律当作编译期常量来定义数组大小。
这些是[Highway quick reference 的 Vector and tag types](https://github.com/google/highway/blob/2191a3487f1aeff1796817884bdddcd4b0bd1810/g3doc/quick_reference.md#vector-and-tag-types)
给出的API约束。

## 本课只比较一个语义：有多少个元素

| 对象 | 32位元素的数量如何确定 | 本课要避免的误解 |
| --- | --- | --- |
| 固定256位向量 | 256/32 = 8 | 8不是所有SIMD目标通用常量 |
| 固定128位向量 | 128/32 = 4 | 把指针步进写成字节数 |
| 可伸缩向量的抽象 | 由目标与运行配置下的tag/lane数确定 | 从最大可能宽度推导当前实际lane数 |
| Highway tag | 使用对应tag的`Lanes(d)` | tag本身不是装着数组元素的容器 |

这里是类型与尺寸的语义比较，没有比较吞吐、频率或端口数。
SVE与RVV的可伸缩向量还涉及目标特有的类型与执行语义，留到必要单元再展开；
今天无需穷举所有指令。Arm资料入口是[ACLE](https://arm-software.github.io/acle/main/acle.html)。

## 一个能推翻错误理解的输入

取两个最大的`int32_t`值，阈值为0。正确和为`4,294,967,294`，它能放进`int64_t`。
如果先用32位有符号C++标量加法计算两者，再转换成64位，加法已经溢出；
事后的转换不能修复之前的运算。在C++有符号标量加法里还涉及未定义行为。
向量API可能有自己的整数运算语义，必须查相应约束，不能把标量UB与某条SIMD指令混为一谈。

另一个常见跳步是：把32位向量循环累加到32位向量寄存器，最后才做64位归约。
最终返回类型为64位，并不能证明中间lane没有先发生溢出。
第06/07单元会讨论扩宽时lane数如何变化，以及何时必须扩宽或分批清空累加器。
今天先把这个问题作为后续验收条件记录下来。

## 标量参考与最小验证

可执行代码：[scalar_reference.cpp](../labs/scalar_reference.cpp)。它逐值比较，
将选中的值转换为`int64_t`后累加，并拒绝超出已经证明安全的长度范围。
它是语义oracle；默认编译器可能自动向量化，因此不能直接当作「一定未使用SIMD」的性能基线。

从xlab根目录运行：

```bash
mkdir -p .local/engineering-daily/build
clang++ -std=c++20 -O1 -g -fsanitize=address,undefined \
  docs/daily/projects/highway/labs/scalar_reference.cpp \
  -o .local/engineering-daily/build/scalar-reference
.local/engineering-daily/build/scalar-reference
```

保留断言，不加`-DNDEBUG`。检查空输入、恰好等于阈值、极值、跨越32位结果范围、
允许的最大输入数和超出限制后的拒绝行为。通过这些测试只支持标量契约与这些边界；
不证明后续Highway实现、其他ISA路径或性能已通过。

后续向量实现的输入矩阵还需加入`N-1/N/N+1/2N-1`、非对齐地址与过滤选择率。
这些是未来验证设计，本课尚未执行向量路径。标量结果一致与内存访问合法要分别检查；
结果偶然一致不能排除越界读取。
