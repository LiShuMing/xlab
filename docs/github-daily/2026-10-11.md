> 状态截止：2026-10-11 07:20 UTC。仅整理公开 GitHub 技术材料；PR 状态与版本发布状态可能在截止时间后变化。

## 关键结论

今天最重要的共同信号不是某个局部优化，而是“派生状态必须忠实对应真正生效的数据与生命周期”。DataFusion 的 CSE 把本应受 `FILTER` 保护的表达式提前到投影，ClickHouse 在 `optimize_on_insert` 合并前计算 skip index 输入，Trino 的 local exchange 把页面留在内存池账外：三者分别破坏了求值域、持久化行集和资源归属。它们提醒我们，优化规则、索引构建和内存记账都不能只看局部算子，必须对齐最终语义边界。

第二个信号是，能力开放应该按“表示是否完整”而不是按表面类型判断。ClickHouse 只让把 NULL 信息完整编码进 key 的四种方法进入 adaptive aggregation，继续拒绝把 NULL 放在旁路 cell 的单 key 方法与 `LowCardinality`。Velox 则选择在构造期拒绝 fixed-point 与 grouped execution 的不安全组合。这两项都不是泛化兼容能力，而是用明确的准入条件把错误结果或卡死变成可解释行为。

把这些案例放到更一般的数据库与查询引擎语境中，可以提炼出三条待验证的工程假设：物化视图、索引和统计信息应对应真正持久化或参与查询的逻辑行集；可缓冲队列应归属统一的查询或 task 内存账户并参与背压；优化规则应把条件求值、key 语义和最坏复杂度作为显式契约。这些 PR 提供了反例、修复方式和实验设计，但只能说明具有相似数据流或状态生命周期的系统值得检查，不能据此判断任何未检视引擎存在同类缺陷。

## IVM

### ClickHouse #123291：派生索引必须在写入合并后计算

[ClickHouse #123291](https://github.com/ClickHouse/ClickHouse/pull/123291) 截止时仍为 open。问题出在 `writeTempPartImpl`：旧路径先计算 sorting key 和 skip-index 表达式，再由默认开启的 `optimize_on_insert` 合并整个 block。对于 `SummingMergeTree`、`AggregatingMergeTree`、`CoalescingMergeTree` 和 `GraphiteMergeTree`，这些临时索引列也会像数据列一样参与合并；例如 `length(name)` 会从真实的 5 被求和成 15，随后索引却描述了最终并未存储的值。查询依赖该索引时可能跳过真正命中的 granule；在 `SummingMergeTree` 中，临时索引输入还会干扰“所有求和列为零则删除该行”的判断，错误保留本应消失的行。

修复把必要的排序表达式留在合并前计算，其余 skip-index 表达式改到合并后、基于最终行重算，与 `MergeTask` 的顺序一致。正确性边界也写得很清楚：结果名与 stored column 同名的索引表达式暂时保留旧路径；历史 part 不会因升级自动全量修复，要等后续 merge 或执行 `MATERIALIZE INDEX`，而被错误保留的零和行也只会在 merge 时清理。

证据方面，新测试在 master 上有 10 个分支失败，修复后 49/49 次随机运行通过。debug 构建中向带 `lower(url)`、`length(url)` 索引的 `ReplacingMergeTree` 写入 400 万行，中位数从 3.48 秒降到 2.15 秒；索引恰好基于排序键 `cityHash64(url)` 时为 2.20 秒到 2.25 秒，基本属于噪声。这证明修复覆盖了已列出的 MergeTree 复现形态，并且“延后无关索引表达式”在给定写入测试里没有形成普遍性能税；它没有证明历史 part 会自动恢复，也没有覆盖所有索引函数、merge policy 和并发写入组合。这里真正的不变量是：用于裁剪的派生状态必须描述查询最终可见的行和值。实现取舍是在合并后重算部分表达式，换取索引与持久化结果一致；只有合并前后输入等价的表达式才有理由保留提前计算。

跨系统适用条件是：写入链路确实包含去重、聚合、合并或行淘汰，而且分区统计、zone map、数据跳过索引或增量视图描述的是合并后的逻辑行。若某种索引被明确定义为覆盖原始事件流，或合并不改变其索引表达式输入，则不能直接套用这个结论。验证时可针对“先算派生列、再做局部聚合或 compact”的路径，让同一批原始行分别走即时合并与延迟合并；最终行集、索引裁剪结果和增量视图应一致，否则需要进一步区分派生状态生成时机与历史数据修复策略。

## 优化器

### DataFusion #26184：CSE 不能穿透条件求值边界

[DataFusion #26184](https://github.com/apache/datafusion/pull/26184) 截止时为 open。SQL 聚合的 `FILTER` 先决定某行是否参与，再对通过的行求聚合参数；因此，被过滤掉行上的失败表达式本来不应执行。旧 CSE 在两个聚合共享参数时把参数提到 aggregate 下方的 projection，使其对每一行求值，于是 `sum(arrow_cast(x, 'UInt64')) FILTER (...)` 与 `count(...) FILTER (...)` 的组合会在已被过滤的负数上触发非法 cast，而单个聚合可以成功。

修复让 `ExprCSEController::conditional_children` 把带 `FILTER` 的聚合参数与其 `ORDER BY` 表达式标成条件子节点；filter 自身仍是普通子节点，因为每行都要执行。窗口聚合也建立同一契约，但当前 window executor 仍未先执行 filter，因此这部分是为后续行为保持正确。安全的提取仍保留：无过滤聚合也使用该表达式，或 filter 自身使用该表达式时仍可抽取；只有表达式仅存在于 filtered aggregate 参数中时才停止提前计算。

测试覆盖单元测试、SQL logic test、有无 `GROUP BY` 的复现、`EXPLAIN` 计划和与无过滤聚合共享参数的安全场景，证明列出的 aggregate plan 不再把失败表达式移出条件求值域，同时仍保留几类安全提取。它没有证明 window aggregate 已具备相同运行时语义，因为 PR 明确说明 window executor 目前还没有先执行 filter；也没有证明所有表达式形态都不会退化。review 已给出一个具体反例：新遍历为了恢复树序，对每个 child 线性扫描 conditional 集合，宽 `CASE` 的 CSE 单阶段测量从 1 万分支约 1.4 ms 增到 39 ms，从 4 万分支 7.4 ms 增到 616 ms，呈 O(n²)。这些数字测的是 CSE 阶段，不是完整规划延迟，因此足以定位算法复杂度，却不能直接换算成端到端查询耗时。

通用约束是：表达式复用、公共投影和 codegen hoist 不能在未证明安全时跨越 `FILTER`、`CASE`、短路布尔运算或 lazy 参数的求值边界。若表达式是无副作用、对全域有定义且不会抛错的 total function，提前求值可能只影响成本；非法 cast、除零、越界和可能抛错的用户函数则会把成本变换升级为语义变化。可用这些失败表达式构造成对聚合，再把表达式宽度扩到 1 万、4 万分支，同时验证结果、异常行为和规划耗时的渐进趋势。

### DataFusion #25798 与实验 #12：接口契约不等于自适应策略已经成熟

[DataFusion #25798](https://github.com/apache/datafusion/pull/25798) 截止时为 open，目标是提供通用 `StageBoundary`：每个 partition 可以先 prime 输入、报告 readiness，外部驱动在检查已物化结果或拿到内存预算后再显式 release 输出。它解决的是 DataFusion 现有 pull-based `ExecutionPlan` 缺少统一“完成输入、检查状态、延迟下游并释放资源”接口的问题。测试覆盖输入完成但不出数、恢复后分区结果不变、预算排队、依赖 boundary、取消、输出丢弃后的 reservation 释放，以及 panic/error 传播。

[edmondop/arrow-datafusion #12](https://github.com/edmondop/arrow-datafusion/pull/12) 则是建立在该接口之上的 draft 实验，作者明确写明不打算合并且代码为 hack quality。它运行时并行观察 hash join 两侧，选择更小的一侧作为 build side。TPC-H SF100、32 核实验中，Q9 的最小可完成内存预算从 14G 降到 9G，无限制时峰值 RSS 从 17.0 GB 降到 12.2 GB，耗时约 12.7 秒到 12.6 秒；但全套没有显著加速，最多慢 3.6%，10G 限制下救回 Q9 的同时让 Q7 失败。原因是 join 要等两侧都被 drain 后才启动，阻断了原本的流水线。

这里更可迁移的方法是把两层问题拆开：先判断系统是否需要统一的 stage 完成、资源 reservation 与 release 契约，再独立评估运行时 replan 策略。只有当输入有界、物化成本可控，而且节省 build-side 内存比损失流水线更重要时，等待两侧信息才可能划算；持续流输入、低延迟首批输出或一侧统计已经可靠时，额外 boundary 可能纯属负担。实验应同时记录峰值内存、首批输出延迟、端到端耗时和被阻断的 pipeline 数量，不能只用 Q9 的内存下降证明策略普适有效。

### ClickHouse #124931：按 part 重复查 patch parts 会把规划放大

[ClickHouse #124931](https://github.com/ClickHouse/ClickHouse/pull/124931) 已于截止前合入 master，修复“表有大量 part、同时存在 lightweight update 的 pending patch parts 时，带 skip index 查询规划很慢”的问题。公开 PR 的 changelog 和提交说明表明，旧路径在规划时会为每个 part 重复查找 patch parts；修复方向是避免这类 per-part 重复工作，并让 text index 能按 part 直接读相关 patch 信息。

该修复已通过 [#125113](https://github.com/ClickHouse/ClickHouse/pull/125113) 和 [#125114](https://github.com/ClickHouse/ClickHouse/pull/125114) 分别合入 26.8 与 26.9 分支，对应版本标记为 `26.8.24.9`、`26.9.16.10`。这只能证明代码已进入分支，截止时尚未核实包含这些提交的正式稳定版是否发布，不能把“已回移”写成“用户已可从稳定渠道升级”。跨系统可检查 planner 是否在 data file 或 segment 循环中重复查询 delta、delete vector、patch 或索引元数据；若元数据已经随 part 常驻且查找为 O(1)，这一优化未必有意义，真正需要收敛的是远端访问、目录扫描或随 part 数重复扩大的关联工作。

## 执行与存储

### Trino #31533：局部 128 MB cap 不能替代 task 级内存记账

[Trino #31533](https://github.com/trinodb/trino/pull/31533) 截止时为 open。原 `LocalExchangeMemoryManager` 只对各自 buffered bytes 执行 128 MB soft cap，没有挂到 memory context；一个 task 有很多 local exchange 时，每个队列都可能“局部合规”，总量却完全不进入 memory pool，memory killer 和 pool limit 都无法响应。作者从一次 OOM 后的 worker heap dump 定位到：fault-tolerant INSERT 同时包含 UNNEST 和多个 window function，8 个 task 的 192 个 local exchange 在池外持有约 16 GiB 页面，超过 pool 上方的 heap headroom。

修复为每个 task 增加共享的 `LocalExchangeMemoryReservation`，把页面 retained bytes 计入 task user memory context。per-page 快路径仍无锁，manager 只在 buffered bytes 跨过 1 MB 步长时上报，因而每个 exchange 最多高估约 2 MB；sink 同时等待局部 exchange cap 和 memory-pool future，池满时生产者进入背压。原有 128 MB cap 的值与语义不变，因此这是新增上层资源归属，不是用全局池替换局部流控。背后的不变量是：只要某个 task 仍拥有队列页面，这部分可释放内存就必须在同一资源治理域可见；设计取舍则是用 1 MB 阶梯上报减少同步开销，接受有界高估和更早一点的背压。

公开证据中的 192 个 exchange、约 16 GiB 来自 OOM 后的 heap dump，它证明“池外存在足以耗尽 headroom 的真实页面”，但不是受控的修复前后实验；PR 说明也没有给出端到端吞吐、锁竞争或 OOM 复现成功率。因此还需要两类验证：一类让 exchange 数量增加而单个队列始终低于 128 MB，确认全局池会在总量达到阈值时阻塞；另一类在消费、取消和异常关闭过程中检查 reservation 最终归零，并比较 1 MB 批量上报对吞吐和峰值误差的影响。

对具有统一资源治理的执行引擎，exchange、shuffle、window、sort、spill staging 和 RPC send queue 的 retained bytes 原则上应落入 query/task 资源树，局部阈值只负责平滑流量。但共享 page、切片视图和跨队列引用会让“逐队列相加”发生重复记账，使用逻辑 payload 又可能低估真实 heap 占用；因此账户口径应与释放所有权一起设计。实验可在每个队列低于局部 cap 的前提下逐步增加 exchange 数，验证统一账户随实际 retained bytes 单调增长、达到 pool 限制时生产端阻塞、取消后 reservation 归零，并记录粗粒度上报与共享缓冲造成的最大偏差。

### ClickHouse #124868：只有完整编码 NULL 语义的 key 才能进入 adaptive aggregation

[ClickHouse #124868](https://github.com/ClickHouse/ClickHouse/pull/124868) 已于截止前合入 master。此前只要 `GROUP BY` key 为 `Nullable`，`AggregatingStep::adaptiveAggregatorRejectionReason` 就拒绝 adaptive aggregator；而 CSV、JSON、Parquet 的 schema inference 常产生 `Nullable` 列，使大量高基数聚合无法进入该路径。此次没有笼统放开类型，而是按 hash method 的表示能力准入：`nullable_keys128`、`nullable_keys256` 把 null bitmap 打进 key，`nullable_serialized`、`nullable_prealloc_serialized` 序列化 null flag，四种方法的 key 值本身足以唯一标识分组，因此 frozen kernel 可以安全地暂存 miss 并直接插入 bucket table。

边界同样重要：`nullable_key8` 到 `nullable_key64`、`nullable_key_string`、`nullable_key_fixed_string` 把 NULL 保存在旁路 cell，暂存时只有 nested default 值，放开会把 NULL 组和默认值组合并，所以仍被拒绝；任何 `LowCardinality` key 也仍被拒绝。这不是“Nullable 全面支持 adaptive aggregation”，而是完整编码语义的四种 key 方法被准入。

正确性测试 `05340` 覆盖 9 个准入和 4 个拒绝形态，把 NULL 放在 nested default 旁边并与普通路径比对，patched 版本 50/50 次随机验证通过。它证明当前四种准入方法在这些类型、NULL/默认值碰撞和执行形态下与普通路径等价，也用拒绝形态约束了 admission gate；它没有证明所有 `Nullable` 组合都已安全，更不表示被拒绝方法永远无法通过新的状态携带协议获得支持。RelWithDebInfo、1 亿行、16 线程、中位数 5 次的性能证据显示：两个 `Nullable` 数值 key 从 1796 ms、10.29 GiB 降到 865 ms、4.53 GiB；数值加字符串从 1820 ms、11.69 GiB 降到 1146 ms、6.94 GiB；含真实 NULL 的三个 key 从 2401 ms、10.47 GiB 降到 1161 ms、6.55 GiB。但 1820 万组且 key 聚簇的场景虽从 510 ms 降到 422 ms，峰值内存反而从 2.06 GiB 升到 3.48 GiB，说明这些 benchmark 证明的是特定分布下的收益与成本反例，不是无条件省内存。

跨引擎的关键判据不是类型名，而是冻结、分桶、spill 或跨线程转移时传递的 key 是否自包含分组等价类所需的信息，包括 NULL 标志，以及具体语义需要的 collation、timezone 或 decimal scale。若实现同时转移了旁路 discriminator，并在落入目标表时走专门的 reinsertion 协议，key 本身不自包含也未必错误；危险的是暂存表示丢失信息却复用普通插入路径。可对每种 key encoder 做“NULL 与 nested default 相邻”的变异测试，并把随机高基数、强聚簇和 spill 三类分布分开测量。

### Velox #19453：把不支持组合前移成构造期错误

[Velox #19453](https://github.com/facebookincubator/velox/pull/19453) 已于截止前合并。fixed-point 的 initial、body 和 convergence sub-task 总是 ungrouped，但 trailing sub-task 复用了 task 的 plan fragment，因此会继承 grouped execution。结果可能是 trailing pipeline 对每个 split group 重读完整输出状态而产生重复结果，也可能永远收不到 grouped split 而不启动。

修复只是在 `Task::create` 阶段拒绝同时包含 fixed point 与 grouped execution 的 fragment，把静默错数或 hang 变成显式错误。PR 同时说明当前没有 caller 使用这个组合；这支持“guard 对现有调用面影响很小”，却没有提供兼容实现、性能收益或 grouped fixed-point 的端到端测试，因此不应拔高为执行架构创新。它守住的最小不变量是：同一份 fixed-point 输出状态只能按其生产模式被消费一次，trailing pipeline 不能隐式改变 split 语义。构造期拒绝适合罕见组合；若该组合成为常用需求，则需要显式 mode 转换或按 split group 隔离状态，而不能长期把拒绝当成支持。

有针对性的验证应同时覆盖单个与多个 split group、trailing pipeline 没有 split 的场景，以及 fixed-point 输出为空和多轮收敛的情况：旧实现应能稳定复现重复输出或不启动，新实现应在创建 task 时给出确定错误，并确认 ungrouped fixed-point 的既有结果不变。这样的测试只能证明 guard 放置正确，仍不能替代未来兼容方案对状态隔离和调度进度的证明。

## 待验证实验

1. **合并后派生状态一致性**：同一输入分别走即时合并和延迟 compact，覆盖重复 key、零和行、map/subcolumn、索引表达式与增量视图。断言最终行集、skip/zone-map 裁剪、统计信息和 MV delta 一致；任何只在强制 materialize 后恢复的结果都视为失败。
2. **条件求值 CSE 变异测试**：在 `FILTER`、`CASE`、`AND/OR` 短路和 lazy UDF 的拒绝分支放置非法 cast、除零和显式异常，比较不开 CSE、开启 CSE 和 codegen 后的结果；再把宽度扩到 1 万、4 万分支，确认规划阶段近似线性而不是 O(n²)。
3. **exchange 统一内存账户**：固定每个队列都低于局部 cap，逐步增加 exchange 数；观测 task/query/pool 三层 reservation、生产者阻塞时点、取消后的释放，以及 retained bytes 与记账值差异。
4. **自包含 hash key 准入**：对每种 nullable/low-cardinality/serialized key encoder 做 NULL 与默认值碰撞测试，覆盖单 key、多 key、spill、two-level、ROLLUP/CUBE；只有 key 本身完整编码等价类的实现才可进入 frozen/adaptive 路径。
5. **stage boundary 成本模型**：复现静态与运行时 build-side 选择，除了峰值 RSS 和成功内存下限，还记录首批输出延迟、总耗时、pipeline 阻塞时间和 Q7/Q9 这类相反样例，避免用单查询内存收益替代全局判断。
