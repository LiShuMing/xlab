## 关键结论

今天最值得精读的是资源和语义合同，而不是把更多算子标成“支持 spill”。DataFusion 的 materialized CTE 把一次计算、多引用回放、每个 reader 的解码预算和多次执行生命周期绑在一起；DuckDB 则暴露了 build/probe 预算口径与 external 状态转换的独立性。能够写盘不等于能在同一内存预算下重新读回。

另一个共同问题是身份必须稳定：Spark 的 memory consumer 要按对象身份注册和触发回收，ClickHouse 的类型转换结果要有真实 owner，Paimon 游标要识别快照内容而不只是编号。MV 路线上，Doris 的 COUNT 空输入语义已有合并修复，StarRocks 的 Iceberg MV 仍是互操作设计，Trino 的 owner-refresh 提案则已关闭，不能把“有更新”统一写成“能力已上线”。

## 优化器与物化执行：DataFusion CTE 的回放预算和生命周期

核验到 2026-10-13 00:41 UTC：[PR #25580](https://github.com/apache/datafusion/pull/25580) 仍 open、未合并，head 为 facf0d51745638db877fa141eac0903341510af1；PR 最后更新 10-12 23:20:46Z。#26229–26233、#26238–26240 是 10-12 新建的八个开放 issue，不能写成八项已实现功能。以下分析读了当前 12 文件 patch、10-12 三个 commit 的差分、相关 review 及八个 issue 正文/评论。

### 今天真正改了什么

10-12 的实质修复是 [6d8f124](https://github.com/apache/datafusion/commit/6d8f12457774c3b7979ef51b04b2b14933da911a)：把大 batch 从内存挪到盘，可能让每个 reader 的“最大解码 batch”预算一起变大，结果越 spill 越缺内存。review 给出的 18MB / 两引用例子最终只占 72B，却请求 49.1MB。新代码先计算“释放的 buffer 字节 − 所有 scan partition 新增的回放预算”，选净收益最大的 suffix；大 batch 按已有盘上 batch 大小估算切片，没有正收益就返回分配错误。新增单测和 18MB SQL 回归覆盖这个形状。[原始复现](https://github.com/apache/datafusion/pull/25580#discussion_r4244985567)

另两次提交分别把 5 行 CTE / 10 万行表的错误 build-side 选择固化为测试并说明统计缺失，以及为原地 reset_state 补注释；都没有修复对应限制。[统计提交](https://github.com/apache/datafusion/commit/ee37c93c6311cdc6338f971d721bccee82899d9d) · [reset 注释提交](https://github.com/apache/datafusion/commit/facf0d51745638db877fa141eac0903341510af1)

### 机制与最容易误读的边界

- 当前补丁把 CTE 拆为 body + continuation 的 producer 和多个 scan leaf，按唯一 id 绑定；首个 scan 触发共享 future，并行跑完所有 body partition，再让每个引用回放内存前缀和 spill 文件。这个 pipeline break 避开同一 hash join 的 build/probe 不同时消费时的有界 fan-out 死锁，代价是首行必须等完整 body。默认和 NOT MATERIALIZED 仍 inline，无自动启发式；当前 parser 要 PostgreSQL dialect。
- id 按每个 logical occurrence、每次 planning run 重编号，避免两个 view 引用或嵌套 ViewTable planning 错绑；已经绑定的 scan 不再重复计入 reader 数。scalar subquery 的 scan 可能在 producer 子树外且先执行，所以绑定必须扫整个计划，不能仅递归 producer 的 continuation。
- outer filter 只进入 continuation；共享 body 保留全部列与自己的结果。特别是 body 本身引用 outer column 时，SQL planner 直接回退 inline，尚未提供“每 outer row 一次 materialize”。未引用的 CTE不执行；有引用且 body 无界时拒绝。递归 term 内的 CTE每轮重算，term 外的 materialized CTE可跨轮共享；不能把这些行为等同 PostgreSQL 的所有默认/volatile 语义。
- ReplayStream 持有整个 MaterializedOutput，使 plan 先 drop 后，buffer、spill 与内存 reservation 仍活到 stream drop。这个生命周期正确性已在单测覆盖，但不代表最后 reader 结束就能提前释放。

### 八个后续 issue 的实质

1. [#26229 reset_state](https://github.com/apache/datafusion/issues/26229)：当前在共享 buffer 上换掉 OnceAsync 并返回 self，违反“新节点、旧节点不变”的接口契约。已 execute 的 scan 持旧输出不受影响；危险窗口是同一 plan 的重叠 run 中，旧 run 延迟启动的 scan 跨过另一次 reset。issue 明确目前无已知 SQL 错结果；per-run / TaskContext registry 是提案，且需兼顾递归轮次与子查询。
2. [#26230 属性](https://github.com/apache/datafusion/issues/26230)：scan 仍报 unknown statistics / ordering / partitioning。它可能让 10 万行表建 hash table，5 行 CTE 当 probe，不能把 materialize 宣传成无条件提速。属性应来自最终优化后的 body，且只有保持对应 partition 映射时才可宣称 ordering/hash partitioning。
3. [#26231 proto](https://github.com/apache/datafusion/issues/26231)：四个 logical/physical 节点没有默认 protobuf 编码；进程间传计划的路径仍不支持。未来编码应传 id、解码后全计划重新绑定；body 和 scan 分处两个进程的问题不能靠序列化本地 Arc 解决。
4. [#26232 byte-bounded spill](https://github.com/apache/datafusion/issues/26232)：今天修复只是局部补救。初次 spill 的 batch 仍整批写，按行切片的内存估算对 dictionary/view/list 与 IPC 写入尺寸也不可靠。issue 提议接入 #25910 的 byte bound，同时保留按 reader 数判断净收益；预算来源尚未定。
5. [#26233 早释放](https://github.com/apache/datafusion/issues/26233)：拟在所有“仍可能执行”的 scan partition 完成/取消后释放。仅统计已启动 streams 会错删迟到 reader 的数据；把从未执行的 partition 永久计数又会泄留。必须与 #26229 的 per-run 生命周期一起设计。
6. [#26238 first-class LogicalPlan](https://github.com/apache/datafusion/issues/26238)：现为 Extension + downcast，优化器/外部消费者不易知道两个 input 的不同角色；拟改 enum variant，届时是下游 exhaustive match 的 API 变更，当前尚未做。
7. [#26239 联合过滤](https://github.com/apache/datafusion/issues/26239)：提议把每个引用的 f1 OR f2 … 下推 body，保留各引用原过滤；任一引用无过滤则不推。只能用确定性、CTE 列上的条件，且不得改变 volatile body 语义。这里是 OR，不是把所有条件相与。
8. [#26240 联合裁列](https://github.com/apache/datafusion/issues/26240)：提议聚合所有引用所需列的并集，再同步 body、scan schema 与上层列索引。引用可能在另一 input 或子查询，单节点 top-down projection pass 不够；当前 necessary_children_exprs 仍要求 body 全部列。

### DuckDB：低内存正确性分别卡在“预算口径”和“状态切换”

- [#27010：external hash join 为 probe 预留预算](https://github.com/duckdb/duckdb/pull/27010)，仍为 draft，最后更新 10-12 23:10:49 UTC。旧逻辑以“最大 build 分区及 pointer table + probe 需求是否超过 reservation”决定重分区，却把整个 reservation 交给 radix-bit 选择器。如果 build 单独装得下、加上 probe 才装不下，就可能进入重分区后触发“build 必须大于预算”的断言。补丁把传入预算改成 max(0, reservation − probe requirement)，与 PrepareExternalFinalize 的预算口径一致；没有改变严重倾斜时跳过重分区的分支。[代码](https://github.com/duckdb/duckdb/blob/54ad89ccc314125f85dea01b0379bdd8a86d052c/src/execution/operator/join/physical_hash_join.cpp#L1884-L1920)

### DataFusion：修好 build 行顺序，不等于已经向 planner 声明排序属性

- 三项新增测试分别检查两批 LeftAnti 输出 10,20,3000,4000、跨 batch 重复键的 inner 匹配次序、强制 HashMap 的 prepared build 布局与索引正确性。前两项遍历 hash-join 配置，prepared 测试用 1MiB pool 并显式禁用 ArrayMap。它们没有直接覆盖 NULL-aware anti、所有 semi/outer 变体或真实 Comet 工作负载。当前返回的六项主要 CI 成功，extended tests skipped；[Codecov](https://github.com/apache/datafusion/pull/26228#issuecomment-6128783299) 报 patch coverage 66.67%，5 行 missing/partial，不能写成全面覆盖。
- [#26235](https://github.com/apache/datafusion/issues/26235) 才是把 LeftSemi/LeftAnti/LeftMark 的 build-side order 写进 maintains_input_order 的后续工作；当前 PR 没有实现 planner 去排序，也不等于无 ORDER BY 的 SQL 获得全局有序保证。未来 LeftSemi 增量输出和 hash-join spilling 还可能破坏这项属性。评审者报告过一组配对 benchmark 未见显著差异，但本日报没有独立复测，不据此给出本地性能结论。

共同启示（源码分析）：这四项不是同一种“省内存优化”。需分别验证 reservation 扣项一致、external 状态能否实际转移、释放对象的身份是否正确，以及物理行布局是否匹配声明的顺序；只看总内存、只看 spill 次数或只看结果集合都可能漏掉问题。


## 执行与内存：减少逐行开销，也要保住异常路径的结构不变量

**P1：LEFT JOIN 的输出填充可以按掩码的连续性分块，而不必改变连接算法。** ClickHouse [#125542](https://github.com/ClickHouse/ClickHouse/pull/125542) 仍开放，当前 head 为 `77d81fa5801a834df622cc95fe8ed6b7489d739c`。当结果要求输出右侧 key 时，`filterWithBlanks` 原先逐行调用虚函数，复制匹配值或插入未匹配默认值。补丁每次将 64 个过滤字节压成掩码：全保留走一次 `insertRangeFrom`，全丢弃走一次 `insertManyDefaults`，混合块和尾部保留原逐行路径。它利用的是匹配模式的局部一致性；随机交错模式不会自动获得相同收益。

`ColumnNullable` 的批量默认值插入并非简单循环替换：先 reserve null map，再写 nested column；若 nested 写到一半抛异常，把 null map 延长到 nested 当前长度后重抛，避免两者行数失配。这里需要的是失败之后仍可安全析构/检查的基本保证，并非承诺整个插入事务式回滚。作者在 x86 release、固定 8 核、21 次取中位数的测试中报告两条受益查询耗时降为 0.61×/0.71×，指令数降为 0.47×/0.55×；无关查询耗时也曾波动至 1.23×而指令数基本不变，说明短时 wall time 不足以解释全部变化。这些是作者报告，本次没有重跑。9,756 条差分查询覆盖字典共享、多种类型和 63/64/65 等边界；反向过滤路径的定向探针未命中，目前主要是代码论证，不能写成所有调用点均被动态验证。

可执行验证应独立扫描匹配率和连续 run 长度，覆盖全匹配、全不匹配、交替、单个异常位、尾块以及 `inverse_filter=true`；同时做 nested column 分配失败注入，断言 null map 长度始终等于数据列长度。跨系统迁移前必须核实批量插入与逐行插入对 LowCardinality、复制列、默认值和异常安全的合同等价，不能只看原始定长数组。

**P0：类型变换返回的新对象，不能只留下解引用后的引用。** ClickHouse [#125533](https://github.com/ClickHouse/ClickHouse/pull/125533) 仍开放，head 为 `be5cb931313d90f470246306fce44f88f36fa8d4`。SummingMergeTree 对名称以 Map 结尾的 Nested 列进行类型检查时，直接将 `*recursiveRemoveLowCardinality(...)` 绑定到 `const IDataType&`。简单 LowCardinality 元素可能仍由原列类型持有；Array/Map 内部嵌套 LowCardinality 则会生成新类型，临时智能指针在语句末尾销毁，后续 key/value 检查留下悬空引用。补丁用具名 `DataTypePtr` 保活至本轮检查结束，不改变聚合语义。

作者报告 25.3.14.14、25.12.11.4 可在 INSERT 触发崩溃，当前 26.x 可能表面输出正确但 ASan 报 UAF；新 SQL 回归覆盖 Array/Map、key/value 位置及 `OPTIMIZE FINAL`，并报告未修复 ASan 失败、修复后 50/50 随机配置通过与原有 44 项 summing 测试通过。版本影响范围与重复测试次数来自作者，尚无本次独立复现，也没有据此确认已回补或发布。最有价值的迁移检查是审计“返回 owning pointer 的类型重写函数被立即解引用”这一模式，并分别测试返回原对象与构造新对象的分支；只用简单类型测试，恰好容易把生命周期缺陷掩盖掉。
