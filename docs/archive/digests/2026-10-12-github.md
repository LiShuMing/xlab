# 数据库工程日报 2026年10月12日

日期：2026-10-12（UTC+8）

今天值得关注的是几类容易被局部优化掩盖的约束：列式数组的共享关系、NULL 的三值逻辑、表达式绑定后的身份，以及文件统计的保守性。优化能否成立，往往取决于这些信息在跨算子、跨批次、跨格式时是否仍然准确。

以下结论来自公开 PR 正文、讨论与相关代码补丁。未合并提案与已合并变更分别注明；文中的性能数字来自作者或审查者报告，本次没有本地运行这些基准。

## Spill 的字节上限必须同时约束共享关系与峰值生命周期

DataFusion [#25910](https://github.com/apache/datafusion/pull/25910) 仍在审查。它处理的场景很具体：输入批次能放进内存池，排序也成功 spill，但落盘时重新拼成按行数限制的大批次，最后的 merge 又因最大批次过大而无法启动。当前实现让排序使用 `max(sort_spill_reservation_bytes / 4, 1 MiB)` 的 spill 批次目标；配置为零时不启用这个目标。四分之一来自最小两路归并及预读的预留需求。归并输出也加了字节估计上限。

新的问题出现在 ListView。多个逻辑行可以指向同一段 child 数据；若 compaction 把每行范围依次复制进新 child，原本共享的物理数据会变成多份。当前补丁的 `compact_list_view` 正采用逐行复制，而 `split_for_spill` 先收集全部 compacted pieces 再开始写。[最新审查](https://github.com/apache/datafusion/pull/25910#discussion_r4243787355) 报告：1,024 行共享一段 64 KiB child 时，约 74 KB 输入可变成约 68 MB 的同时存活 pieces，落盘也膨胀到约 67 MB。这些是审查者的复现数字。

这里有两个独立问题。逐块 compact、立即写出可以缩短临时对象生命周期；保留重叠 child 区间的共享关系，才能同时抑制磁盘体积和后续 merge 预留的放大。仅修复前者仍会留下后者。当前输出字节数来自平均行宽估计，也未全部纳入内存池，因此不能把目标值当作硬内存上限。单条超宽行、IPC padding、Union/REE 等仍有明确边界。

建议验证：把共享比例作为独立参数，分别构造完全共享、部分重叠、不共享的 ListView；同时测逻辑行数、落盘字节、最大解码批次、池内预留和进程峰值。再做删除输出 cap、禁用共享保持的消融测试，避免“查询终于成功”掩盖更危险的进程内存增长。

## 多列 NOT IN 的内存与 NULL 配对成本可以分开优化

DataFusion 两个尚未合并的 PR 分别处理不同瓶颈。[#26213](https://github.com/apache/datafusion/pull/26213) 允许多列、带 scope key 或 join filter 的 null-aware `LeftAnti` 转为以子查询侧构建的 `RightAnti`。这样，大外表可以流式 probe 小子查询；每个 probe batch 独立记录 UNKNOWN 行，不再需要按原大外表行数长期保存 build 状态。

补丁保留了 SQL 三值逻辑：精确匹配使 NOT IN 为 FALSE；涉及 NULL 且不能证明 tuple 有确定不匹配的候选，使结果为 UNKNOWN。join filter 也随输入交换。它不会对 build 去重，因为有过滤条件时这种简化不一定成立。PR 的内存回归使用 200k 外表行、101 子查询行和 2 MB 限制，并比较 join reordering 开关。作者报告的是小侧构建带来的内存改善；NULL 候选配对本身基本没有减少。

[#26214](https://github.com/apache/datafusion/pull/26214) 才进一步缩小候选集合。若 tuple 的某一对应元素在两侧的当前作用域里都不能为 NULL，它只可能相等或形成确定不匹配，可以作为 scope key。代码把 nullable 元素放在前面计入 `null_aware_value_keys`，非空元素随后作为范围限定。例如 `(a,b) NOT IN (x,y)` 中 b、y 都非空，a 为 NULL 的行只需检查 y=b 的子查询行。

边界也很重要：仅外侧非空不足以这样重排；nullable、不可哈希的元素仍受限制。没有 NULL 的查询可能为提前构建 scope hash map 付出额外成本。作者的小规模基准已有这样的轻微退化，因此不能把有 NULL 的收益推广到所有分布。

建议验证：采用 `NOT EXISTS ... IS NOT FALSE` 形式作结果参照，覆盖空子查询、全 NULL、单侧非空、多 nullable 元素、关联过滤以及 LeftMark/OR 场景。把内存预算、NULL 比例和 scope key 基数分别扫描，检查优化的收益来自小侧构建还是配对数减少。

## Iceberg 写路由应使用分区变换后的值

Doris [#68921](https://github.com/apache/doris/pull/68921) 仍未合并。原来的 random 分发会让多个 writer 同时接触大量 Iceberg 分区，增加小文件，也容易碰到每 writer 默认 128 个打开分区的限制。新方案由 FE 按语句开始时固定的 schema 和 partition spec 顺序传递源列与 transform，BE 复用 Iceberg 分区函数，先执行变换，再对结果 hash 路由。

原始列值的 hash 不能代替分区值的 hash。以 `truncate[10]` 为例，11 与 19 属于同一分区，20 与 29 属于另一分区；对原始数值分发仍可能把同一物理分区拆给不同 writer。补丁的测试直接断言这两组输入分别落到同一 channel，也检查 schema 更名之后仍使用语句固定的路由名称。回归中，200 个 identity 分区、300 个 day 分区的各 10,000 行写入分别得到 200 和 300 个文件，每分区最多一个文件。

这个结果有适用范围。新路由要求 BE execution version 至少 17；旧 BE、nested source 和无分区表保留 random 回退。未知 transform 会报错，不能悄悄退回原值 hash。`SKEWED` writer assignment 允许热点分区扩展到多个 writer，所以“一分区一个文件”只是这些回归的结果，不是全负载承诺。

建议验证：混合版本升级时比较 FE 分发说明与 BE 实际路由；覆盖 schema rename、bucket/truncate/day 变换、热点分区和 writer 扩容，同时统计每分区 writer 数、打开分区峰值及文件大小分布。只检查总行数无法证明路由正确。

## 函数输入域推导与文件统计必须共同保留 NaN

Trino [#31330](https://github.com/trinodb/trino/pull/31330) 是仍在审查的大型接口提案。`DomainPreimage` 把 `f(x)` 落在某个输出域的条件转换为 x 的输入域，并区分 EXACT 与 CONSERVATIVE。后者可以多读，但不能遗漏真正匹配的输入，通常仍需要 residual predicate 或 join 复核。它希望让比较改写、domain extraction 与 dynamic filtering 使用同一套函数语义。

浮点 NaN 使“范围”与“集合”的区别变得实际。文件的有限 min/max 不一定描述其中的 NaN；若只按有限边界构造域，`x <> 1` 等谓词可能把含 NaN 的文件整块剪掉。[审查提出的这个问题](https://github.com/trinodb/trino/pull/31330#discussion_r4242533962) 已在当前补丁中处理：`IcebergSplitSource` 读取 `nanValueCounts`，只有明确为零才排除 NaN。缺少整张统计 map、缺少该字段统计、或计数大于零，都保守地把 NaN 加回有限边界域。

新增测试分别覆盖 REAL/DOUBLE，以及 Parquet/ORC 中有限边界为 1、同时包含 NaN 的文件。`x <> 1`、`NOT(x < 2)` 和 `IS DISTINCT FROM 1` 都应保留对应 NaN 行。这里应描述为当前代码已经补上统计链路，不能继续把旧审查意见当作未修缺陷。

接口代价同样需要保留：`function_preimages_enabled=false` 可以走旧的部分优化路径，但 NaN 相关 SPI 变化并不会一起关闭；受影响插件需要重新编译，一些旧 range API 也无法表示带 NaN 的集合。建议对比新旧开关下的结果、文件扫描数与残余谓词，并覆盖缺统计、全 NaN、混合有限值、NULL 和函数异常输入。公开合同对原函数成功的输入约束精确性，不应额外推导为对所有异常行为的完全等价保证。

## 失败路径必须同时守住任务状态和对象生命周期

ClickHouse [#125283](https://github.com/ClickHouse/ClickHouse/pull/125283) 修复 pipeline expansion 分配失败后的两条独立路径，目前仍 open。

第一条是取消竞态。扩图失败标志在锁内已经可见，但失败线程尚未完成 executor cancellation；另一线程可能得到 Cancelled，跳过 pushTasks，却继续执行自己上一次准备的旧 task。外部排序此前已重置 `merge_sorter`，重执行就会访问失效状态。当前补丁在没有更新任务的分支显式执行 `context.setTask(nullptr)`，把“没有新任务”落实到线程上下文。

第二条是异常日志触发的 use-after-free。扩图到一半的 processors 原本由 ExecutingGraph 保活，pipeline ports 仍保存指向它们的指针；graph 销毁后，异常处理中的 processor profile 日志仍可能顺着这些指针访问对象。补丁把未完成登记的 processors 转移到 pipeline 自己的 processors 列表，由其拥有到后续日志完成。

测试组合了高并发、低 external-sort 阈值和 `executing_graph_add_node_fail` 注入，期待查询返回内存异常且进程持续存活。作者还报告分别撤回两个修复时能重现 debug 崩溃与 ASan UAF；保留两个修复时多轮通过。这些反证使“两个修复分别必要”比单纯一次绿灯更可信，不过 race 测试仍是概率性的，failpoint 也未覆盖 processor 已登记后才失败的去重 catch 分支，那里目前只有代码审阅证据。正文限定为 master 分支问题，不能直接推断 26.9 也受影响。

建议验证：为每条失败分支单独画清 task、graph、processor、port 的拥有关系；在 cancel、日志、析构之间逐一注入失败。把“返回预期错误”和“后台线程及异常日志没有继续访问半销毁状态”分成两组断言。

## 可复现性能测试也要披露地址布局与安全取舍

ClickHouse [#125278](https://github.com/ClickHouse/ClickHouse/pull/125278) 提议对实际启用 ThinLTO 的 Linux amd64/aarch64 release 构建恢复 position-dependent `ET_EXEC`，原因是 PIE 恢复后部分进程出现依赖装载地址的热循环退化。作者报告的慢进程退化范围为约 15–40%，涉及同一版本对自身反复运行的对比，不是查询算法被替换。作者在自己的 Intel Granite Rapids 机器上未复现该慢模式；这项依据主要是 CI 统计与地址布局干预，不能把所报退化幅度写成补丁已经独立实测收回的收益。

当前 CMake 条件已经限定为 `ENABLE_THINLTO && !ENABLE_TESTS && !SANITIZE && RELWITHDEBINFO`。早期审查认为只检查 ThinLTO 开关会错误扩大范围，[该条件已修订](https://github.com/ClickHouse/ClickHouse/pull/125278#discussion_r4243764890)。其他构建仍保留 PIC/PIE，兼容性检查新增 ELF 类型验证。

这个提议仍未合并，并有明确安全成本：可执行代码失去 ASLR，heap、stack 与共享库的随机化仍保留。它不应被写成可以直接采用的免费性能收益。更稳妥的评估是把发布构建方式、可执行文件类型、装载地址、同进程重复与跨进程重复分开记录；同时评估是否存在保留安全属性的布局或工具链修复。若一个 benchmark 只重复同一进程，可能完全看不到这种差异。

## 展示名称与嵌套字段位置都需要在正确阶段绑定

DuckDB [#26844](https://github.com/duckdb/duckdb/pull/26844) 与 Spark [#59387](https://github.com/apache/spark/pull/59387) 都未合并，但它们揭示了相似的元数据问题。

DuckDB 的 `struct_update(c0, a := c1)` 在 bind 时已经知道要更新字段 a。后续 filter pushdown 可能通过 `NormalizeColumnRefAliases` 改写参数 alias；若执行和统计阶段再次用 alias 查找目标字段，原本更新 a 的操作就可能被误认作新增字段，向双字段结果写入第三个字段。补丁把 argument→field 索引存到 `StructUpdateBindData.field_indexes`，执行、statistics 和 SQL unbind 共用这份已绑定语义。新增回归覆盖下推比较、更新加新增、投影、NULL，并用 `struct_insert` 对照。旧序列化计划没有该字段时会读成空映射，当前未见新增跨版本恢复测试，仍应单独验证这一边界。[实现](https://github.com/duckdb/duckdb/blob/a47d39358f8891fa37850064e9ca882af1b60dd7/extension/core_functions/scalar/struct/struct_update.cpp)

Spark 的问题发生在 DSv2 nested schema pruning 之后。源报告 s.y 排序，最初绑定为 `GetStructField(s,1)`；把 struct<x,y> 裁为 struct<y> 后，外层 ExprId 没变，y 却移到了 ordinal 0。只检查 ExprId 会留下过期排序表达式，使已有排序与查询需要的排序无法匹配，多加一个 SortExec。补丁用 `ProjectionOverSchema` 按裁剪后的字段名称和类型重绑；缺字段时截断普通排序前缀；KeyedPartitioning 仍可保留后续有效的分区键排序。正例断言保留 y 时无需 SortExec且结果正确，反例则确认裁掉原排序字段后仍补 SortExec。逻辑 relation ordering 保持原样，继续服务于 PlanMerger。[实现](https://github.com/apache/spark/blob/28d5adb4e62621af1b27504600cebd665a4a932f/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/v2/DataSourceV2ScanExecBase.scala)

两者给出的工程提示是：执行语义应该依赖稳定的绑定结果；物理布局变化后，ordinal 等布局相关信息又必须重建。建议把 alias 改写、列重排、嵌套剪枝、序列化恢复串成测试矩阵，同时断言结果和计划形状。只有“结果没错”的测试容易漏掉冗余排序，只有“少了算子”的测试又可能漏掉语义身份被替换。

## 可以直接复用的验证习惯

- 同时量化逻辑工作量与物理资源：行数正确不代表共享buffer、落盘字节或峰值预留合理。
- 对优化做消融：删掉关键 guard、身份检查或内存约束后，回归必须真的失败。
- 让负例和正例成对：无 NULL 对有 NULL、字段保留对字段裁掉、精确统计对缺失统计、单版本对混合版本。
- 固定代码版本与运行条件，分清作者复现、审查意见、当前 diff 已修内容与尚未独立执行的测试。

这些变化适合用于设计回归和评估实现边界。开放 PR 的代码和结论仍可能继续变化，采用前应复核最终合并版本及对应发布说明。
