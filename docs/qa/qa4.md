## 第一部分：题目

### 一、算法与工程编码

**Q1（核心题）：用 Python 设计“相同请求只计算一次”的并发服务。**

多个调用方同时请求同一图片的同版本特征，希望只执行一次推理，其余调用方共享结果。失败后允许重试，不要求缓存已完成结果。

**追问：** 一个调用方超时，是否取消共享推理？不同图片持续涌入，如何限制内存和并发？

**思考提示：** 先定义请求等价条件，再画出“查找、创建、等待、清理”的并发过程。

**Q2（选做题）：为长音频实现流式切片器。**

题设：输入为解码后的单声道音频采样流，按固定时长切片，相邻切片有重叠，末尾不足一片也保留。

**追问：** 如何避免把整段音频读入内存？重叠片段的下游结果如何合并？

**思考提示：** 明确采样率、样本下标和区间边界；用短输入验证最后一片。

### 二、推理框架与多模态模型

**Q3（核心题）：共享长提示词的请求，为什么可能加速 Prefill，却仍然 Decode 很慢？**

题设：同一模型服务收到大量共享系统提示词、用户输入不同的请求，计划引入前缀缓存。

**追问：** 相同图片能否直接视为相同前缀？缓存命中后，哪些计算仍然存在？

**思考提示：** 分开讨论视觉编码、语言模型 Prefill、Decode；列出缓存复用必须满足的条件。

**Q4（选做题）：需求只写“语言识别”，你会怎样澄清和设计链路？**

输入可能是文本、音频，也可能是带字幕的视频。

**追问：** 判断音频属于哪种语言，与语音转写有什么区别？什么情况下值得调用大模型？

**思考提示：** 先确定输出契约、混合语言与未知语言的处理，再讨论模型选型。

### 三、操作系统与软硬件性能工程

**Q5（核心题）：单样本推理很快，但整条链路吞吐很低，如何定位大量小操作的开销？**

题设：每张图片都单独做预处理、传输和模型调用，GPU 时间线上出现大量短任务和间隙。

**追问：** 如何区分 CPU 提交慢、传输碎片化与 GPU 计算慢？为什么加大 batch 不一定有效？

**思考提示：** 画出一个批次的 CPU、传输、GPU 时间线，设计只改变一个因素的实验。

**Q6（选做题）：服务退出显示 OOMKilled，但没有模型显存不足异常，如何调查？**

**追问：** 为什么宿主机内存充足，容器仍可能被杀？增加预取为什么可能触发这个问题？

**思考提示：** 区分主机内存、容器限制、共享内存与 GPU 显存，先取得退出原因和事件证据。

### 四、分布式数据 Pipeline 与异构调度

**Q7（核心题）：CPU 解码和 GPU 推理，应该融合在一个 Worker，还是拆成两个阶段？**

题设：图片解码成本波动大，模型加载成本高，解码后的数据比压缩文件大很多。

**追问：** 拆开后如何避免中间数据传输成为瓶颈？融合后如何避免 CPU 工作阻塞昂贵 GPU？

**思考提示：** 比较数据膨胀、模型副本、独立扩缩容和故障恢复成本。

**Q8（选做题）：两类 GPU 都能运行模型，但显存与速度不同，如何分配混合请求？**

题设：短文本、小图、大图请求混合到达；部分大图请求只能在大显存卡运行。

**追问：** 为什么按请求数量平均分配可能更差？如何避免小请求占满大卡，导致大请求长期等待？

**思考提示：** 先定义可运行条件，再区分资源适配、预计执行成本与公平性。

### 五、可观测性、稳定性与项目经验

**Q9（核心题）：请用一个真实案例解释，你参与的多模态 Shuffle 调度解决了什么问题。**

从输入、数据流、调度对象和瓶颈开始，说明个人职责及验证方法。

**追问：** 调整前后哪些阶段成本发生变化？如果局部 Shuffle 更快、整体产出却没提升，怎样解释？

**思考提示：** 区分你已实现、参与讨论与计划验证的部分；准备一张前后数据流图。

**Q10（选做题）：推理服务成功率上升，为什么有效数据产出反而可能下降？**

题设：发布后 HTTP 成功率提高，但下游可用样本减少。

**追问：** 应怎样定义业务成功？监控标签能否直接包含图片 ID、请求 ID？

**思考提示：** 把接口成功、推理完成、质量合格和最终提交拆开统计。

## 第二部分：练后核对

### A1：共享进行中的计算

维护“请求键 → 共享计算”的映射；创建与登记必须互斥，已有请求等待同一结果。键应覆盖内容身份、模型和预处理版本、影响输出的参数。

单个等待者取消通常不应自动取消其他人共享的计算；底层超时与无人等待后的处理要另定策略。完成或失败后清理，并核对映射仍指向该次计算，避免误删后续重试。

平均每次查找为 O(1)，元数据空间随活跃键和等待者增加。**误区：只限制推理并发，不限制等待者和待处理请求。**

### A2：用样本位置定义切片

将窗口时长和步长转换为整数样本数，要求 `0 < 步长 ≤ 窗口`；明确采用左闭右开区间。保留下一片需要的重叠数据，流式读取并处理尾部。

总读取为 O(N)，若复制输出，成本还取决于重叠后的总输出量；工作缓冲为 O(窗口大小)。测试空流、短流、恰好整片和非整数时长换算。

**误区：重叠能保留上下文，却也可能造成转写结果重复。**

### A3：缓存减少重复上下文计算

有效前缀缓存可复用符合条件的历史 KV，减少重复 Prefill；新输入仍需处理，后续 Decode 仍需计算并读取历史 KV，因此长上下文的生成成本仍在。

复用要求模型、输入表示、位置与相关配置兼容。相同图片不代表完整前缀相同，也不能默认视觉编码缓存与语言模型 KV 缓存是同一个机制。

**误区：把前缀缓存理解为缓存整段回答。** 具体支持范围应按实际 vLLM 版本和模型核验。

### A4：先澄清任务，再选择模型

文本语言识别输出语言类别；音频语言识别判断说的是哪种语言；ASR 输出说话内容。视频还需要澄清识别音轨、字幕还是画面中的文字。

简单分类任务可先评估专用模型；再考虑大模型是否带来必要收益。要覆盖静音、噪声、短输入、混合语言与拒识。

**误区：用转写是否成功，替代语言识别准确率。**

### A5：分析时间线，而非只看利用率

分别测量 CPU 预处理、提交间隔、传输次数和字节、GPU 执行及等待。用合成输入隔离模型，用预处理完成的数据隔离解码，再改变批次观察瓶颈。

合批可能摊薄提交与传输开销，但会增加等待、填充、显存和尾延迟。异步 GPU 操作需等待相关执行完成才能正确计时。

**误区：把 CPU 调用返回时间当成 GPU 完成时间。**

### A6：先确认哪种内存耗尽

检查容器退出状态、内存峰值、cgroup 限制与 OOM 事件，再分析解码缓冲、预取、进程副本、锁页内存和共享内存。

容器可能先触及自己的上限；GPU 显存不足是另一类故障。预取应按实际占用字节设预算，不能只限制条目数。

**误区：看到 OOM 就直接缩小模型。**

### A7：融合与拆分没有固定赢家

融合减少中间传输，可能提升局部性；拆分便于分别扩缩容和复用模型服务，但需要有界缓冲、背压及合理的数据布局。

用端到端有效吞吐、单位成本、峰值内存和失败重算量比较。CPU 波动、解码后数据膨胀与网络条件共同决定方案。

**误区：只比较单算子耗时，忽略阶段间的数据成本。**

### A8：先满足约束，再优化分配

先按模型兼容性、显存预算和输入限制过滤设备，再依据预计耗时、排队与截止时间分配。为只能运行在大卡的任务保留机会，可结合配额、老化和有界预留。

成本预测需持续校正，并覆盖预测偏低时的 OOM 或重排策略。

**误区：GPU 利用率相同，就代表有效产能相同。**

### A9：真实职责与证据优先

建议按“负载与约束 → 瓶颈证据 → 我的职责 → 方案取舍 → 对照验证 → 限制”回答。

你的参与范围已知；具体调度粒度、实现、负载及收益仍待补充。局部优化可能被下游瓶颈、额外开销或工作量变化抵消。可迁移能力是阶段拆解、数据移动与调度判断。

**误区：将参与研发描述成独立负责整套平台。**

### A10：以最终有效产出定义收益

分别统计接收、推理完成、质量合格、去重后提交及重试；同时观察数据分布，防止通过丢弃困难样本“改善”成功率。

指标使用有界标签；请求 ID、图片 ID 放日志或 trace，避免指标基数失控。成本分母应包含最终有效样本，失败和重试成本也应计入。

**误区：HTTP 200 等于业务成功。**
