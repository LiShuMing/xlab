针对 **AI 平台／训练与推理基础设施**岗位，最快的准备方式是：**围绕一个小型训练与推理项目，准备 10 道核心题、4 个实验、1 道系统设计题。** 每道题都用实验结果支撑，比单纯背 API 更有效。

先按 **3 天准备、单机可运行、有 GPU 再加测**安排。

**一、优先准备这 10 道题**

| 面试题 | 回答必须覆盖 |
|---|---|
| 1. Ray 在 AI 平台里解决什么问题？ | 分布式任务和有状态进程管理；Data 处理数据、Train 组织训练、Serve 承载在线推理 |
| 2. Task 和 Actor 如何选择？ | Task 适合独立计算；Actor 常驻进程、保留状态，适合加载模型、复用连接 |
| 3. 一次远程调用经过哪些组件？ | 调用方提交任务，节点上的 Raylet 管理资源与调度，Worker 执行；GCS 是全局元数据服务，不必逐个中转所有任务 |
| 4. `num_gpus=0.5` 意味着什么？ | 逻辑资源配额和设备可见性；**不保证一半显存，也不保证硬件隔离** |
| 5. 多卡训练为什么会一直 Pending？ | 资源是否足够、Placement Group 是否能整体预留资源、放置策略、节点与 GPU 配置 |
| 6. Ray Train 和 PyTorch DDP 有什么分工？ | Train 管工作进程、环境和恢复；DDP 负责梯度同步，GPU 通信通常依赖 NCCL |
| 7. Worker 或 Actor 崩溃后会怎样？ | 区分任务重试、进程重启、状态恢复；重启 Actor 会重新执行构造函数，内存状态不会自动恢复 |
| 8. 如何设计训练 checkpoint？ | 模型、优化器、训练步数、随机数状态；需要精确恢复时还要处理数据读取进度 |
| 9. Serve 如何提高吞吐并控制延迟？ | 副本数、并发、动态批处理、排队与背压；同时观察吞吐、P95 延迟和错误率 |
| 10. Ray Serve 与 vLLM、Kubernetes 分别负责什么？ | Serve 管服务编排与请求路由；vLLM 管模型执行及相关优化；Kubernetes 管容器与节点资源 |

每道题按这个结构练成 **2 分钟答案**：

> 问题是什么 → Ray 如何处理 → 有什么限制 → 我用什么实验验证过。

**二、做这 4 个实验**

**实验 1：模型常驻与资源调度，约 45 分钟**

用一个小模型或 NumPy 计算，对比：

- 普通 Task：每次调用加载模型。
- Actor：在构造函数中加载一次，后续复用。
- 改变 Actor 的数量和 `num_cpus`，观察并发与排队。

记录模型加载时间、首次调用延迟、预热后吞吐、进程内存。

要能解释：**Actor 为什么适合模型常驻？副本增加为什么可能先加速、随后遇到瓶颈？** 首次加载和稳定运行的数据要分开。

**实验 2：Actor 崩溃与状态恢复，约 45 分钟**

创建一个计数器 Actor，明确设置 `max_restarts`，只终止实验自己创建的 Actor：

1. 先把计数器加到 10。
2. 触发进程退出，观察重启后的值。
3. 加入持久化，再观察恢复结果。
4. 为请求增加唯一 ID，讨论重试时如何避免重复更新。

要能解释：**进程恢复、业务状态恢复、请求恰好执行一次，是三个不同问题。**

**实验 3：双 Worker 训练与 checkpoint，约 90 分钟**

用 `TorchTrainer` 训练一个很小的分类模型：

- 单机两个 CPU Worker，先验证训练流程。
- 固定总训练步数和有效 batch size，对比单 Worker 与双 Worker。
- 保存 checkpoint，在固定步数触发一次故障，然后恢复。
- 有两张 GPU，再测 GPU 版本。

记录训练吞吐、loss、checkpoint 大小和恢复耗时。

要能解释：**小模型为何可能越并行越慢？恢复后为何可能重复读取部分数据？**

CPU 实验能证明流程与恢复行为；多 GPU 通信性能需要实际 GPU 实验。

**实验 4：Serve 压测与自动扩缩容，约 90 分钟**

部署一个小模型接口，按顺序对比：

1. 固定 1 个副本。
2. 固定 2 个副本。
3. 开启动态批处理。
4. 设置自动扩缩容，施加低流量 → 高流量 → 低流量。

记录每秒成功请求数、P50/P95 延迟、错误率、副本数变化、模型加载时间。比较时固定输入、机器资源和压测方式，并先预热。

要能解释：

- 批处理何时提高吞吐，何时增加等待时间？
- 为什么配置扩容后，延迟仍可能暂时升高？
- Serve 增加副本与集群增加节点如何衔接？

**三、用一道系统设计题串起来**

> 设计一个支持离线训练、批量推理和在线推理的多租户 AI 平台。

画出这条链路：

**数据存储 → Ray Data 预处理 → Ray Train 训练 → 模型与 checkpoint 存储 → Ray Serve 部署 → 请求入口**

重点讨论 5 件事：

- GPU 配额、排队和多卡资源预留。
- 数据加载与计算之间的背压。
- 训练失败、checkpoint 与恢复。
- 模型发布、预热、灰度和回滚。
- 吞吐、延迟、错误率、GPU 利用率与成本。

如果岗位偏大模型，再补：连续批处理、KV cache、张量并行，以及这些能力与 Ray 的分工。

**四、3 天怎么分配**

| 时间 | 任务 | 产出 |
|---|---|---|
| 第 1 天 | Core 基础＋实验 1、2 | 一张架构图、资源与容错题答案 |
| 第 2 天 | Train＋实验 3 | 一份训练性能与故障恢复记录 |
| 第 3 天 | Serve＋实验 4＋模拟面试 | 一张压测对比表、一份平台设计 |
