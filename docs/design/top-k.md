# 海量数据 Top-K 设计

> 主题：在大规模数据上求 Top-K 的方案选型、正确性依据与工程陷阱。
> 适用范围：面试系统设计题、查询引擎 TopN 算子实现评审、在线服务热点统计选型。

## 结论先行

不是"海量就要分布式"，而是先判断哪个约束真正起作用：

```
K 个元素放得下内存？
├─ 是 ┬─ 无 GROUP BY    → 单遍流式最小堆，O(K) 内存，一遍扫完
│      └─ 有 GROUP BY   → 先完整聚合再 Top-K（不可在分片内截断）
└─ 否 ─┬─ 需要精确      → 外部排序 / 外部 quickselect（多趟分区）
       └─ 允许近似      → Space-Saving / Count-Min Sketch，O(K) 空间单遍
```

真正决定方案的是 **K 与内存的关系**、**是否允许近似**、**是原始行还是聚合后再排序**。N 的大小几乎不参与决策。

## 一、先把"海量"拆成四个正交约束

| 约束 | 取值 | 影响 |
| --- | --- | --- |
| N 与内存 | 能否一次读入 | 几乎不影响（见结论 1） |
| K 与内存 | K 个元素能否常驻 | 决定"堆"还是"外部排序" |
| 精度 | 精确 / 误差 ε 可接受 | 决定是否引入 Sketch |
| 语义 | 原始行 Top-K / 分组聚合后 Top-K | 最关键，决定能否局部截断 |

第 4 项最容易被忽略，也最容易导致错误方案：`ORDER BY x LIMIT K` 与
`GROUP BY g ORDER BY SUM(v) LIMIT K` 看起来只是多了一个分组，可行性却完全不同。

## 二、三个反直觉结论

### 结论 1：内存装不下 N，对 Top-K 没有影响

维护"最大的 K 个"只需要一个大小为 K 的最小堆，**单遍扫描、O(K) 内存**。
100 GB 数据、1 MB 内存、K=10 毫无压力。听到"海量"就上分块和外部排序，是把
Top-K 误当成了排序问题。

只有当 **K 本身装不下内存**（例如取前 10%、K 达千万级）时，才退化为选择问题。

### 结论 2：分布式必须每节点输出 K 个，而不是 K/P 个

设全局前 K 为 \(S\)，任取 \(x \in S\)。若 \(x\) 不在其所属分片的局部前 K 中，
则该分片至少有 K 个元素大于 \(x\)；这些元素都在全局集合里且都大于 \(x\)，
于是 \(x\) 不可能属于全局前 K —— 矛盾。故

\[
S \;\subseteq\; \bigcup_{i=1}^{P} \mathrm{TopK}_i
\]

这条**截断可并性质**是所有分块与分布式方案的正确性根基，也把网络代价钉在
\(O(PK)\)。"每节点取 \(K/P\)"是最常见的错误答案：它会让每个分片丢掉自己
本来可能进入全局前 K 的元素。

### 结论 3：聚合后的 Top-K 不能局部截断

`GROUP BY g ORDER BY SUM(v) LIMIT K` 中，分片内的排名没有意义：某个 key 在分片 A
只累计到 100、在分片 B 上有 1000，A 内的低排名完全是假象。必须让**同一个 key 在
所有部分和汇总之后**再参与排名。

区别在于聚合结果是否可跨分片合并、以及合并前能否截断：

| 聚合 | 分片结果可分片合并 | 合并前能否截断 |
| --- | --- | --- |
| `MIN` / `MAX` | 可以（单调） | **可以**，分片 MIN 的 MIN 即全局 MIN |
| `SUM` / `COUNT` | 可以（可加） | **不可以**，必须先按 key 求和 |
| `AVG` | 需 `(sum, count)` 对 | 不可以 |
| `COUNT(DISTINCT)` | 需 sketch 或集合 | 不可以 |

这条区分直接对应两个不同的执行计划：前一种是"局部 TopN + 归约"，后一种是
"全量按 key 聚合 + 单点 TopN"。

## 三、分层方案

### 3.1 单机·内存内（K 远小于 N）

维持大小为 K 的**最小堆**（求最大的 K 个），堆顶就是"准入线"：

```text
for each x:
    if heap.size() < K:          push
    else if x > heap.top():      pop; push
```

这个前置判断是全部优化所在：被拒绝的元素只花一次比较，并且**不分配任何内存**。
理论复杂度 \(O(N\log K)\)，但绝大多数元素停在前两行，实测常数接近 \(O(N)\)。

选型分界：\(K \le N/100\) 用堆；K 与 N 同阶时改用 `nth_element`（平均 \(O(N)\)，
耗时几乎与 K 无关），只要最终 K 个有序再对前 K 排序。

### 3.2 单机·K 巨大（K 个元素装不下）

退化为选择问题：k 路外部归并排序，或外部 quickselect（每趟扫一遍统计"小于 pivot
的个数"，共 \(O(N/M)\) 趟 I/O）。此时才需要分块、缓冲池、多趟归并整套手段。

### 3.3 分布式

两阶段：各节点独立维护 K 堆 → 汇总到一个节点做 P 路归约。
数据倾斜（热点 key 或范围热点）时，对分区键加盐或改用 range 分区做二次切分。

### 3.4 流式 + 允许近似

Space-Saving / Misra-Gries：\(O(K)\) 空间、单遍、给出"真实频次误差不超过 \(N/K\)"
的保证，适合 K 大且数据只读一遍的场景（热点词、Top URL）。
代价是结果不精确且可能包含假阳性，不能用于计费类场景。

## 四、查询引擎里的 TopN 算子

`Sort + Limit` 应融合为 TopN 算子，几个必须做对的点：

1. **比较键早于堆操作**：先取排序键与堆顶比较，通过才构造/反序列化整行。
   堆里存 `<key, rowid>` 而非整行，省内存带宽。
2. **谓词与投影下推**：过滤发生在入堆之前，投影只保留排序键和输出列。
3. **zone map / min-max 只能否证**：某数据块的最大值 ≤ 当前堆顶时整块跳过；
   但**不能**用最小值 ≥ 堆顶来"证明"整块入选。Top-K 需要定量信息而非布尔信息，
   这个非对称性在优化器里很容易写错。
4. **有序输入可早停**：扫描天然有序（索引顺序、有序分区）时读满 K 行即可终止，
   \(O(K)\) —— 这是 LIMIT 下推真正值钱的地方。
5. **tie-breaking 必须显式定义**：`ORDER BY score LIMIT 10` 在 score 大量相等时，
   不同并行度会给出不同结果。必须补唯一键做稳定排序
   （`ORDER BY score DESC, id ASC`），否则分布式结果不可复现，回归测试随机失败。
6. **并行归约**：每个线程/分区各维护局部 K 堆再归并；K 过大时 spill 到磁盘。

## 五、坑清单

1. 每节点取 \(K/P\)（结论 2 的反例）
2. 在 Map 端对聚合结果做 Top-K 截断（结论 3 的反例）
3. 求"最大的 K 个"却用最大堆（应该用**最小**堆把最差的顶在上面）
4. 忽略 tie-break，导致结果不可复现
5. 浮点 `NaN` 破坏全序：`NaN` 与任何值比较都为假，堆的 sift 会静默产生垃圾结果，
   必须先定义 NaN 的排序位置或过滤
6. 边界：`K == 0`、`K > N`、`N == 0`、全等值输入
7. **只测小规模**：K 取小了看不出 \(O(NK)\) 与 \(O(N\log K)\) 的差别，
   这类缺陷要在 N 翻倍时观察耗时是否线性才暴露

## 六、如何验证一个 Top-K 实现

- **对拍**：小规模用全排序取前 K 比较集合（tie-break 规则两侧一致）；大规模自校验
  —— 分块求 Top-K 的并集，必须与单遍流式结果完全相同。这条断言正好把"可并性质"
  变成可执行检查。
- **不变量**：堆大小始终 \(\le K\)；堆内任意元素 \(\ge\) 堆顶；结果 size = min(K, N)。
- **复杂度守门**：N 从 1e5 → 1e6 耗时比应在 10 倍附近；明显超出说明常数里藏了
  \(O(K)\) 或 \(O(N)\) 的隐式扫描（典型是每步复制容器）。
- **倾斜专项**：全部元素相等、99% 集中在一个 key，确认堆行为与内存不退化。
- **变异测试**：故意把"每节点取 K/P"写成正式实现，断言对拍必须失败。
  否则"两边都错得一样"的对拍会给出假绿。
