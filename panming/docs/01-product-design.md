# 盘铭产品设计

## 1. 定位与愿景

**一句话定位：把每天的信息输入，转化为有证据、有个人理解、可持续更新的知识作品。**

名字“盘铭”呼应“苟日新，日日新，又日新”。“每日”是持续吸收的节律；“铭”是经过理解后留下的结构。产品的价值取决于用户能否更好地思考、写作、检索和应用，不以保存链接或生成文章的数量衡量。

完整闭环：采集 → 消化 → 阅读 → 选题 → 写作 → 编入图书馆 → 复习与实践 → 新输入。CLI 适合研究过程中的快速采集与脚本，Server 承接持续处理和日级报告，Web 承接阅读、判断、编辑与知识导航。

## 2. 用户、问题与使用场景

### 2.1 首要用户

首版服务一个长期研究数据库、AI 或其他专业主题的个人用户：每天有 10–50 条输入，关注 5–20 个来源，在浏览器、终端、编辑器和 AI 对话之间切换，希望积累自己的文章、研究专题与图书馆。数量是设计负载假设，需用试用数据验证。

后续用户：技术作者、产品研究者和小型研究团队。首版采用单 owner / 单 workspace 体验，数据从开始带 `workspace_id`，为以后隔离做准备；团队协作、组织权限和公开社区不属于首版。

### 2.2 主要痛点

| 痛点 | 现有行为 | 盘铭的结果 |
| --- | --- | --- |
| 输入分散 | 链接在书签，笔记在文件，思考在 AI 对话 | 原始内容与上下文归档到同一个素材库 |
| 收藏后不消化 | 囤积未读链接，不知道今天该看什么 | 每日 Report 有主题、优先级和来源状态 |
| 摘要不等于理解 | 看过模型概括，却说不清自己的判断 | 区分外部事实、模型推断、个人观点与实验 |
| 写作起步困难 | 有素材但缺少可写的问题、结构和证据 | Blog Brief 提供中心问题、章节、来源和缺口 |
| 同一知识反复丢失 | 重复问 AI，难以找到之前的结论 | 图书馆按概念与专题组织，更新可比较 |
| 新信息冲击旧结论 | 旧笔记不会提醒“已经过时” | 来源变化触发受影响知识的待复核标记 |
| 自动处理缺少信任 | 不知道模型读了什么，是否漏掉来源 | 覆盖率、失败原因、引用和版本都可查看 |

### 2.3 Jobs to be Done

- 研究时：保存素材只需一个动作，允许尚未分类、暂时没有正文。
- 每天结束时：花 5–10 分钟知道今日输入中哪些值得深入、哪些改变了旧认识。
- 写作时：从一个问题进入，看到现有证据和自己的观察，完成一篇有立场的文章。
- 几周后：从概念或问题找到旧文章、来源及最新修订，能够用自己的话解释。
- 使用受限平台时：即使不能自动抓取，也能通过粘贴、截图、字幕或导出完成归档。

## 3. 四层内容体系

### 3.1 层级契约

| 层 | 用户问题 | 输入 | 持久产物 | 提升条件 |
| --- | --- | --- | --- | --- |
| Layer0 原始素材 | 我收到了什么，来自哪里？ | URL、Markdown、视频/字幕、Repo、AI 对话、笔记 | Material、原件版本、规范化文本、采集上下文 | 可解析；隐私与模型处理策略允许 |
| Layer1 归纳 | 它说了什么，与我有什么关系？ | 固定版本的 Layer0、兴趣分类 | 摘要、知识卡、主题归类、每日 Report | 引用可回溯；不确定性被表达 |
| Layer2 博客 | 我对此形成了什么理解？ | 多日素材、知识卡、个人注释、实验 | 选题简报、大纲、文章草稿、人工采纳版本 | 用户修改/采纳；事实与观点分开 |
| Layer3 图书馆 | 这些文章如何构成稳定知识？ | 已采纳的 Layer2、必要的原始证据 | 概念页、专题、章节、阅读路径、复习记录 | 人工采纳整合提案；有依赖与更新机制 |

Layer0 的“原始”包括用户自己的想法，但须标明 `user_note` 或 `ai_conversation`，不能自动当作外部事实。四层是语义关系，不是把文件从一个目录移到下一个目录；提升内容后原素材仍保留。

一个素材可参与多个主题、多篇博客和多个知识条目。一篇博客可横跨多日；一份 Report 的选题可与既有选题合并。新知识通过“新增 / 补充 / 反驳 / 替代 / 待实验”联系到旧知识。

### 3.2 分类、Topic、Series、Library

- **Category**：稳定的大类，如数据库、AI、个人方法。分类有层级，但首版编辑深度限两层。
- **Topic**：一个长期问题，如“数据库算子的外存执行”。有关注问题、别名、排除词、关联来源和知识条目。
- **Series**：用户管理的写作/阅读系列，明确受众、顺序和篇章目标，如“执行引擎学习札记”。
- **Library**：用户构建的书架、书籍、章节与概念链接。章节顺序由用户决定，图关系支持跨书复用同一条目。

自动分类先给建议和理由；用户修正更新可编辑的规则与偏好版本。主题合并保留旧 ID 的重定向、原引用和历史分类，不批量改写旧 Report。

## 4. 每日体验

### 4.1 典型一天

1. 09:00：用户在 Web 收到订阅更新；CLI 保存一篇 Markdown，并附“为何保存”。
2. 12:00：粘贴一段 AI 对话，按会话角色保存；勾选允许哪些内容用于归纳。
3. 16:00：阅读素材，写下一个反对观点或实验结果，进入个人理解区。
4. 21:30：Server 开始生成当日 Report；这是默认开始时间，可修改，不能承诺此时已生成完成。
5. 晚上：用户浏览 3–7 条重点，确认 1 个写作题，查看 2 个待验证问题；可以没有可写题。
6. 周末：将多日素材写成博客，采纳为 Layer2；把稳定结论编入图书馆并排复习。

### 4.2 每日 Report 产品契约

日级归属默认 `Asia/Shanghai`。Report 展示日期、时区、输入截止时间、版本和覆盖情况；时间改变只影响后续日程。历史版本保留原时区和输入范围。

| 区块 | 内容 | 读者动作 |
| --- | --- | --- |
| 今日概览 | 收集/去重/已归纳/受限/失败/晚到数量；输入截止时间 | 明白是否漏读、有何处理障碍 |
| 今日值得读 | 3–7 条重点，重要性理由与证据 | 打开原文、标记有价值/略过 |
| 按主题归纳 | 新事实、与旧知识的差异、不同观点 | 修正主题、补注释 |
| 关注更新 | 博客/人/项目的新项及来源健康状态 | 查看更新、暂停噪声来源 |
| 个人研究输入 | AI 对话、笔记和实验带来的问题 | 确认个人观点、补充实验 |
| 博客素材包 | 0–3 个候选选题、论点、大纲和缺口 | 采纳、并入既有题、延期、拒绝 |
| 知识修订建议 | 哪个图书馆条目可能受影响及原因 | 发起复核；不直接改写知识 |
| 待验证与待处理 | 缺原文、矛盾、抓取失败、预算不足 | 重试、粘贴正文、设置下一步 |

重点数量和博客选题数量均为默认上限，不能为了填满卡片编造内容。无新输入时生成简洁的“今日无新素材”状态，可附到期复习；来源失效时显示“本日未完成采集”，不写“今天没有更新”。

### 4.3 晚到、失败和重跑

每日自动任务先冻结截止时刻之前的输入版本，再生成 Report。21:30 以后收到的素材继续进当日列表，界面提示“未纳入 v1”。用户可更新当日 Report 为 v2；若未更新，下一期以“前日补录”展示，引用原采集日期。不会默默漏掉晚到素材，也不会把前日补录写成当天发生的新闻。

某项素材在截止前收到、但解析尚未完成：v1 的覆盖栏记录它，允许部分报告；处理完成后进入新版或下一期补录。重跑使用缓存归纳，新增 Report 版本，保留用户批注；自动重试沿用同一次运行身份。

`complete` 表示本期冻结输入全部得到明确处理结果，不表示世界上的信息完整。`partial` 表示正文缺失、执行失败、预算延期或预期来源未完成；`no_updates` 仅用于所有预期来源检查成功且输入为空；`failed` 表示没有可阅读的有效产物。

### 4.4 个人理解与写作习惯

初始偏好显式填写：语言、研究领域、想解决的问题、阅读篇幅、写作受众、结构偏好、需要源码/实验的深度。推荐“中文内部学习 + 可选英文外部文章”，由用户选定。

学习反馈优先使用“有价值 / 无关 / 已知 / 待验证 / 我不同意”和人工主题纠正。浏览时长只作辅助，不根据一次点击改写个人画像；每周展示偏好调整建议，允许恢复旧版本。

## 5. 从素材到博客

### 5.1 选题工作台

每个 Blog Brief 必须回答：要解释的中心问题是什么？为何值得现在写？现有素材支持哪些结论？有何个人观察？哪些部分还需要实测或进一步阅读？

支持四种写作任务：技术深入、比较综述、实践笔记、观点短文。文章模板包括背景、核心问题、解释、实例/实验、边界、来源。选题引用的素材版本被冻结；继续补资料时新增简报版本。

### 5.2 人机协作写作

LLM 可生成候选标题、论点图、大纲和草稿，用户可逐节采纳和编辑。用户修改过的正文是新的人工 revision，生成建议保存到旁路；“重写全文”需要明确命令并显示 diff。版本冲突提示选择保留双方或另存版本。

文章标记 `draft → in_review → accepted → archived`。`accepted` 表示用户确认它可纳入个人知识，独立于外部发布。首版只导出 Markdown 与资源清单；公开发布作为后续连接，需要用户明确触发。

AI 研究材料的结论保留 `model_inference` 标签，不能因为被改写为博客就变成已证实的事实。引用原文、用户推断与代码实验分别显示。

## 6. 从博客到图书馆

### 6.1 图书馆对象

用户创建书架与书：例如“数据库执行引擎”，章节为“数据布局 / Join / Aggregate / Sort / 外存与调度”。概念条目可以是“Grace Hash Join”“内存撤销”“来源可信度”，并跨章节复用。

Layer3 的内容结构：概念定义、解决的问题、模型/边界、例子、与其他概念的联系、来源与相关博客、仍未解决的问题、修订历史。

### 6.2 整理与复习

每次采纳博客后提出可选的图书馆变更：新增概念、补充例子、更新某节、标记冲突。用户看 diff 后采纳；重复采纳返回既有关联，不重复建章。

初版复习使用可解释规则：默认 3 / 7 / 30 天，用户选择“能解释 / 模糊 / 忘记”，相应延长或缩短间隔；用户也可指定复习日期。阅读或打开页面不自动算消化。

新素材反驳既有论断时，把依赖条目标记 `needs_review`，展示理由与新证据。历史知识保留；用户复核后采纳新版本。更换标签、翻译正文等非语义变化不触发所有下游重写。

## 7. 三种产品形态

### 7.1 CLI

最重要动作是 `capture`：文件、目录、URL、stdin、笔记和对话导出。目录导入默认遵守隐藏/忽略规则，显示清单，显式白名单才导入隐藏内容。文件变更生成新版本；本地文件删除不自动删除已归档素材。

第二组动作是 `process/report/blog/library/search/export`，支持 JSON 输出、任务等待、失败重试和指定日期补跑。CLI 实际调用同一个 Server API；未来的本地 server profile 仍沿用同一业务协议。

Server 不可达时，`capture --offline` 可保存到本机待上传箱；成功落盘显示“本机待上传”，不显示“服务器已归档”。同步确认后保留短期恢复副本。

### 7.2 Server

持续消费新素材，按来源计划采集，解析与归纳，组织每日 Report，提供引用、搜索、版本和导出。任务状态、来源健康、预算和运行历史对 CLI/Web 可见。

首版自托管在一台服务器；关闭 Web 不影响处理，关闭本机 CLI 不影响服务器日程。Server 停机后的补跑范围明确，默认最近 7 日逐日处理，不把所有遗漏合并成今天。

### 7.3 Web

主导航：今日、素材、每日 Report、主题、写作台、图书馆、关注来源；设置与运行信息置底。今日页同时提供当天素材列表与生成内容入口，Report 是阅读路径而不是另一个难以发现的目录。

支持原文/归纳对照、来源证据抽屉、批量分类、日期筛选、搜索、文章编辑、章节导航和复习。移动端首先保证保存、阅读和简单注释，完整写作与结构编辑以桌面为主。

## 8. 功能范围与优先级

| 能力 | P0 · 内容闭环 | P1 · 持续关注 | P2 · 深化 |
| --- | --- | --- | --- |
| 捕获 | URL、MD/TXT、笔记、AI 对话 Markdown；视频链接/字幕归档 | PDF/OCR、更多对话导出格式 | 音视频转录、浏览器扩展 |
| 关注 | 手动触发、GitHub/RSS 试采集 | RSS 与 GitHub Release 的持续日程 | 更多授权平台、变更订阅 |
| 归纳 | 引用知识卡、人工分类修正 | 主题新旧知识对照、噪声偏好 | 更复杂冲突分析 |
| Report | 手动/每日自动、partial 与补录、Markdown 导出 | 多主题篇幅、每周回顾 | 个性化系列节律 |
| 博客 | 选题、大纲、草稿、编辑采纳与导出 | 跨日选题合并、素材更新提醒 | 外部发布连接 |
| 图书馆 | 书/章节/概念、整合提案、简易复习 | 依赖失效与引用传播、检索问答 | 图谱浏览、章节重构 |
| 搜索 | 元数据/全文/标签 | 可选 embedding 与混合检索 | 语义发现、复杂知识关系 |

任意内容都可以先进入 Layer0：不支持的格式保存原件并显示 `stored_only`，不会承诺能够立刻理解每种格式。首版不自动登录社交平台、不采集整台电脑聊天历史、不提供无来源的自动研究结论。

## 9. 成功指标

北极星指标：每周至少一个被用户采纳且可追溯的“知识推进”，包括形成可解释概念、完成博客、修正旧认识或完成实证练习。统计唯一推进事件，避免同一篇文章反复采纳刷数。

| 指标 | 计算方法 | 14 天试用目标 / 性质 |
| --- | --- | --- |
| 激活 | 首次保存 3 项 → 阅读 Report → 采纳 1 个写作或概念建议 | 首次 30 分钟完成，待验证 |
| Report 阅读收益 | 用户回答“减少了整理时间/明确了下一步” | 两周至少 8 天认为有帮助 |
| 消化率 | 已人工处理的唯一素材 / 可处理唯一素材 | 较基线提高；不设造假硬阈值 |
| 写作转化 | accepted blogs / accepted briefs，观察 14 日窗口 | 两周至少 1 篇有个人修改的博客 |
| 引用覆盖 | 应引用的事实段落中有有效来源的比例 | 自动草稿目标 100%，语义另测 |
| 检索可用性 | 预设 20 个个人问题命中可用内容比例 | ≥80%，以人工相关性评估 |
| 整理负担 | 每日人工整理耗时 | 目标 ≤15 分钟，不含正式写作 |
| 成本 | 日均 token/费用/失败调用 | 可见并在用户设定预算内 |

## 10. 关键产品取舍

归档优先于精确分类；证据优先于顺滑文案；个人修改优先于自动覆盖；一份有用的 Report 优先于大量自动博客；可导出的文件与引用优先于只能在平台内使用的锁定格式。

默认提供“把今天消化完”的轻量路径，但用户可以跳过、忽略、延期。知识输入不形成连续打卡惩罚；待处理素材可批量归档或不再关注，避免产品变成新的焦虑来源。

尚待试用验证的默认项：21:30 生成时间、Report 篇幅、图书馆复习节奏、最有价值的来源组合。实施时按上述默认推进，不阻塞首个闭环。
