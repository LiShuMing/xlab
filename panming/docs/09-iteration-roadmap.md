# 盘铭 · 从可操作原型到持续使用

2026-10-07。基于 [本轮实测](08-functional-audit-2026-10-07.md) 和现有 01–06 设计。下面是建议 backlog，不是已经开发的功能，也不是工期承诺。

实施状态更新：v0.3 可靠性内核已交付；v0.4 已实现离线 mock 的持久任务与证据纵向切片，详见 [11](11-v04-evidence-foundation.md)。实际模型、语义 Topic Delta 与真实素材人评未完成，不据此提前宣布 v0.4 退出门槛通过。

0.4.1 后续更新：已有 LLM API 的真实 Digest 与调用账本已接入，见 [12](12-v041-existing-llm-api.md)。语义 Topic Delta 与真实素材人评仍待完成。

## 1. 当前最值得解决的三件事

1. **放心存**：我的判断不会丢，引用和导出不会换版本，能搬走并恢复。
2. **少花时间理解**：报告告诉我“今天推进了什么、与已有知识有什么关系”，不只是把开头几段排成卡片。
3. **形成持续知识**：文章能变成概念、问题、实验和章节；新的证据能修正旧认识，复习能反馈理解。

当前原型已经验证收集 → Report → 写作 → 采纳的操作路径。但“节省整理时间”和“知识长期复用”尚未经过真实试用验证。**下一版先保证可靠性；随后做一条真实 AI 消化的纵向链路，再扩大来源覆盖。**

## 2. 迭代顺序

| 版本建议 | 核心价值 | 必须先有 | 退出标准 |
| --- | --- | --- | --- |
| v0.3 可信工作台 | 放心写、放心导出、可恢复 | 当前四层闭环 | P1 全关闭；草稿不丢；统一 SourceRef；备份恢复验证 |
| v0.4 有证据的消化 | 从今日输入发现问题与新意 | v0.3 + durable jobs/policy/budget 的最小实现 | 真实素材上的摘要有引用、推断有标记；用户能判断是否省时；无自动覆盖 |
| v0.5 持续输入 | 不必每天手动搬运可信来源 | 可重试任务、采集去重、覆盖账本 | RSS/GitHub Releases 可持续增量；来源失败可见；日报可补录且不重复 |
| v0.6 活的图书馆 | 知识复用、修订、复习 | 冻结来源和人工接受的变更提案 | 一个真实主题完成章节/概念重构；源变更影响可追踪；能检索并回答研究问题 |

部署是独立门槛：只有需要服务器长期运行时才推进 owner/auth/token、反向代理、密钥管理和恢复演练。单机 localhost 阶段不提前扩成多人协作产品。此顺序可根据 14 天真实使用证据调整，但可靠性门槛不取消。

## 3. v0.3：最小可信内核

### 3.1 草稿与冲突（最高优先）

把草稿视为独立对象，而不是“同一 blog 一个 localStorage 槽位”：

- 标识：workspace、blog_id、editor_id、base_revision、draft_revision、content_hash、更新时间。
- 每个窗口拥有自己的草稿；保存成功只清理明确匹配的那个 draft/hash。
- 多窗口变更通过 storage/BroadcastChannel 通知；通知不能自动清除他人的未保存内容。
- 编辑草稿与 accepted revision 分开。确认动作只改变采纳状态，不触碰本机分支。
- 409 页面显示 base/local/server 三方对照；提供人工合并、保留为副本、下载本机稿和明确放弃。
- 本机草稿恢复时提示存在几个分支；存储失败显式警告，保留内存内容和下载入口。
- 之后可增加服务端自动保存，但先避免把冲突中的旧正文自动写回服务器。

测试门槛：双窗口保存/确认/刷新交错、路由切换、网络中断、存储满、浏览器重开；每条分支都能找回。PM-W01/W02 是最小回归。

### 3.2 统一证据契约

建议用一个 SourceRef 贯穿所有入口：

```json
{
  "material_id": "material_…",
  "material_revision": 1,
  "blob_hash": "sha256…",
  "anchor": {"type": "line_range", "start": 3, "end": 5}
}
```

这是建议 schema，不是现有 API 参数。服务端从受信的 revision 解析内容，不能让客户端自报任意原文充当权威快照。

使用范围：Report manifests、Blog 创建、Entry 来源、正文链接、证据抽屉、导出资源清单。选择“最新版”是另外一个显式动作；旧引用不能默默更新。导出 API/CLI 增加 revision 与 raw/markdown 格式，下载按字节处理，附校验 hash。

先保留现有 ID/revision 和 JSONB 历史，做向后兼容迁移。未冻结的体验数据回填需明确标记 reconstructed，不伪装为当时真实快照。

### 3.3 输入与范围契约

- 全部写 DTO 统一标题 trim、正文 NUL、URL/Origin 解析和 ID 类型校验。
- 单独 RevisionConflict 异常，不把全部 ValueError 变成 409。
- 所有确定性校验在 put_blob 前完成；文件/数据库提交间保留恢复信息和孤儿扫描。
- Report 选题支持选材料/拆分；31/50/100 份材料的点击路径与后台限制一致。
- Report 的 cutoff/watermark 在冻结输入时确定；通过输入 sequence 或可证明的 snapshot 协议实现。
- 统一“待解析 / 可阅读 / 有摘录 / 已归纳”状态；短文、代码、空摘录不冒充完成了语义整理。
- 修复首次设置并发初始化、导入默认 tab 和启动 PID/端口竞争。

### 3.4 最小备份与测试门禁

提供 workspace export/restore：对象、修订、来源关系、原件、hash manifest、schema version。凭据不随内容包导出；恢复到独立数据库/目录，验证对象数、引用版本和原件字节，不能只验证 ZIP 能解开。

构建门禁分两类：正常路径持续通过；已知缺陷显式列出，并为目标版本执行 `--runxfail`（必须 0 failed）。浏览器 CI 加入草稿交错、历史导出、旧证据写作和移动收集。定期备份自动化与完整遗忘按后续设计推进，不声称这次最小导出已解决所有恢复场景。

## 4. v0.4：真正有用的每日消化

### 4.1 做一个可度量的纵向切片

首个切片：Markdown/AI 对话/粘贴正文 → 可追溯 Digest → Topic Delta → Daily Report → 用户选择 Brief → 人工写作。先用同一个真实研究主题，例如数据库执行与 Spill；不要求每日强制产文。

Report 应回答四个问题：

- 今天出现了哪些值得读的线索？为什么与我有关？
- 哪些是已知内容，哪些推进了已有主题，哪些与旧认识冲突？
- 我可以围绕哪个中心问题继续写，证据够不够，还差什么？
- 下一步是阅读、实验、提问还是修订旧条目？

正文结构建议：3–5 条重点上限、按主题的新增/重复/冲突、最多 0–3 个 Brief、未完成采集与待补正文、到期复习。数量是上限，不是填充配额。

### 4.2 技术先决条件

模型长任务不能继续放在当前短事务 HTTP handler：

- Job/PipelineRun 持久化；租约、fence、重试、checkpoint、幂等交付；模型调用不占数据库事务。
- Provider adapter 先 mock，再接一个实际 provider；云调用前严格执行 processing_policy。local_only 在没有本地模型时降级提取，不能静默外发。
- 预算 reservation、最终 usage、失败释放、每日上限与用户可见成本；不自动尝试多 provider 花费。
- 固定 revision/chunk 作为模型输入；保留 prompt/model/schema versions 与 provenance。
- 结构化 claim：来源陈述、模型推断、个人判断分离；引用必须指向已纳入输入。
- 校验“引用存在且版本正确”是机械保证，不等于“引用支持结论”。支持性检查仍需质量评估与人工纠错。
- 提示注入素材当数据处理；生成结果不直接修改数据库权限、不调用网页工具、不自动发布。
- AI 只给 suggestion/diff；用户正文、accepted Blog/Entry 继续由显式采纳控制。

### 4.3 质量评估而非只测按钮

准备不少于 30 份允许处理的公开/合成/用户授权素材，包含长文、代码、AI 猜测、相互冲突、重复转载、无正文和旧文章。人工标注重点、来源和不确定性；维护版本化评估集。

硬门槛：所有引用 ID/revision/hash 可解析；local_only 云外发次数 0；人工正文自动覆盖次数 0。研究指标：摘要遗漏/错误、Brief 采纳、冲突识别、用户纠错、每日整理时间。质量阈值先标注试验性目标，再用真实样本校准，不宣称自动事实核验。

## 5. v0.5：输入自动化与信噪比

优先两个合法、可增量的来源：RSS/Atom 与 GitHub Releases。公众号/X/知乎/reddit 等先维持链接、粘贴、文件或正式授权导入；平台限制、授权范围和成本另行确认，不把绕过访问限制写成产品能力。

每个 connector 具备：capability、cursor、last_attempt/last_success、错误分类、限流退避、暂停、去重事件 ID、内容版本 hash。Report 展示 planned/succeeded/failed sources；失败不能显示“无更新”。

调度区分素材轮询、Digest Job、用户 timezone 的日级 Report occurrence。相同日期重跑、停机补跑、晚到输入、取消与重复交付都有回归用例。关注清单必须能编辑、暂停、删除与查看健康状态。

收集效率：浏览器快捷收集入口、选中文字+URL+保存原因、Markdown 批量导入预览、常见 AI 对话导出格式。先做文件/手动入口可验证的增量价值，不一次覆盖所有媒体格式。

信噪比：自定义 topic、批量重分类、主题合并、已知/无价值反馈、近似重复候选。相似内容只建议合并，原始 Capture 与版本不删；同一内容标题不同、转载 URL 不同的规则需可解释。

## 6. v0.6：图书馆不只是文章副本

将知识组织为研究问题、概念、章节、实验与文章的关系，而不是增加更多展示卡片。

- Entry 可人工修订，拥有自身 revision 和 diff；Book/Chapter 可排序、移动、合并。
- 同一概念多篇博客提供整合提案；保留各观点与证据，不能把不同条件的结论强行统一。
- 来源变更通过依赖关系标记 needs_review；显示哪些 claim 可能受影响，保留旧知识直到人工判断。
- Weekly Review：本周解决/未解决的问题、新证据、被修正的旧认识、下一步实验。
- 复习从“点能解释”升级为复述/回答/实验记录；自评与真实可解释程度分开记录。
- 检索先提供过滤、全文、版本化证据返回；RAG 问答作为检索上的能力，只返回有引用的答案，不替代持久知识条目。
- 回收站保护引用可解释性；完整 purge 覆盖 snapshots/exports/index/cache，恢复时重放独立 tombstone 账本。

验收案例：用数据库执行引擎主题，将 Hash Join/Spill/Aggregate/Sort 的数篇文章重构为一章，保留算法边界与实验；新实验否定一条旧判断后，可定位受影响段落并人工修订。能完成这个案例才算验证 Layer3 的重构价值。

## 7. 14 天试用与决策

先修 v0.3，再在实际研究中每天导入约 5–20 条授权输入。样本只用于验证，不自动外发或上传埋点。

| 假设 | 观察方式 | 决策方向 |
| --- | --- | --- |
| 消化比收集更痛 | 分别记录收集/阅读/整理耗时；每天评价一份 Report | 整理最慢则优先 v0.4；搬运最慢则在 v0.4 中提前一个收集入口 |
| 每日 Report 值得阅读 | 记录实际打开、证据点击、纠错与形成的下一步 | 每日噪声过多则尝试 topic/weekly 模式 |
| Brief 能帮助个人写作 | 两周尝试完成至少一篇有个人修改的文章，记录弃用原因 | 标题泛化则优化问题发现，不追求生成字数 |
| 图书馆能复用知识 | 第二周用检索找到并复述第一周条目 | 只收藏不复用则优先问题/复习入口，不先做大图谱 |

原设计北极星仍是“每周被采纳且可追溯的知识推进”。建议同时记录：草稿丢失 0、错误版本引用 0、未处理输入 backlog、Report 用户纠错率、采纳后的修订次数、来源重复率、任务成功率与成本。演示数据和机械重复采纳不计入价值指标。

上述数量是试用目标，不是已取得的数据。默认只本机记录最小事件，不把正文放到分析日志。两周后据证据选下一轮，避免把所有 01–06 功能一起开发。

2. SourceRef + versioned export/raw CLI + 旧证据写作（PM-A02/A03、PM-W03/W04）。
3. 输入/错误 DTO + 初始化锁 + Markdown parser + blob 校验顺序（PM-A04–10/A12）。

前两个包可独立验证；第 4 个需要使用第 2 个的证据契约。完整 v0.3 验收后，再开启模型/订阅的外部调用配置。执行清单在 [TASKS.md](../TASKS.md)。
