# 高优先级持久化修复

范围：修复“大文档可写不可读”和“同步全量保存占用界面线程”。Core Data 模型、数据库位置及 schemaVersion 1 保持兼容，不要求迁移到 SwiftData。

## 大文档恢复

`Workspace.decode` 用于内部工作空间，不再误用备份导入的 50 MB 上限。外部文件改走 `readBackup/decodeBackup`，先读取当前文件大小，再进行有上限的读取；避免把超大文件全部读入内存后才拒绝。文件大小使用实时属性查询，避免同一 URL 替换文件后缓存旧大小。

回归：保存包含 50,000,001 字符私人日记的工作空间，由另一个进程重新打开并比较整个对象；普通旧版 pretty JSON 仍可读取。外部备份导入当前仍限制 50 MB，本地数据库不受此限制。

## 后台保存与明确的状态

- `LocalStore` 改为 actor，首次打开、验证、JSON 编解码及 SQLite I/O 都在后台；Core Data 使用 private queue context。数据库写入使用紧凑 JSON，导出仍使用易读格式。
- `SaveQueue` 用 200 ms 防抖合并连续编辑，同时最多有一个写入任务和一个最新待写快照。较旧的写入完成不会把较新的状态标记为已保存。
- `AppStore.commit` 现在表示“领域操作已接受到内存”，不是“数据库已经落盘”。界面明确显示保存中/已保存/保存失败；编辑框文字进入工作空间后即使写入失败，也留在可见状态中供重试和导出。
- 写入失败保留最新快照，显示重试入口；不回滚到旧状态覆盖之后的编辑。
- 正常退出绕过防抖、等待所有已提交修改。失败则取消退出并恢复操作；等待时拒绝新业务修改。未提交草稿仍使用原来的退出提示。
- 恢复备份先等待当前保存，再生成恢复前备份；恢复期间禁用编辑，只有新文档写入成功后才替换 UI。导出编码和导入解析也移到后台。

## 回归覆盖

`./scripts/check.sh` 包括原有 19 项核心检查、普通/大文档两个独立进程的读写检查，以及 20 项持久化队列检查：

- 100 次连续修改合并为一个最新快照。
- 旧写入阻塞时继续编辑，最终只保留最新内容，写入不并行。
- 旧写入失败时不丢弃更新的待写快照。
- 写入失败不错误显示已保存；重试成功后清除失败。
- 正常退出等待落盘，等待期间不能插入新修改；失败取消退出并保留可见编辑。
- 外部文件大小预检，以及旧版普通备份兼容。

失败与并发测试使用可控制的存储替身；大文档读写测试使用真实 Core Data/SQLite。它们不读取用户日记或真实凭据。

## 性能复测

与原报告相同的数据形状：每天 10 个任务，每任务 3 条事件、250 个中文字符的说明、2 个步骤。日期改为截至当前的历史记录以测试真实 AppStore 提交。

| 数据规模 | 修改后主线程提交耗时 | 后台编辑并完整保存 | 保存期间主线程探针最大间隔 |
| --- | ---: | ---: | ---: |
| 30 天 / 300 任务 | 0.10 ms | 18.1 ms | 2.1 ms |
| 180 天 / 1800 任务 | 0.59 ms | 129.8 ms | 2.6 ms |
| 365 天 / 3650 任务 | 0.88 ms | 245.4 ms | 2.9 ms |

之前一年规模约 266 ms 的完整保存阻塞主线程；现在这部分在后台，主线程提交低于 1 ms。并非完整保存变为低于 1 ms，也不是 UI 全帧渲染耗时。这是本机单次探索性测量，不是 p95 或 Instruments 结果。

## 仍然存在的边界

当前仍保存完整文档，后台总开销随历史增长；独立实体、增量事件、分段加载属于后续优化。强制结束进程或断电时，尚未显示“已保存”的修改可能丢失；本轮没有实现崩溃恢复草稿。

原报告中的两个 P2（编辑后状态撤销、私人草稿阻塞 AI 回顾）已在后续修复，见 [工作流修复与回归](workflow-fix-2026-09-18.md)。
