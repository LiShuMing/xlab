# 实现设计补充

状态：早期实现约束，尚无对应 Swift 实现。当前 C3 的统一编码入口为 [技术设计与实现方案](technical-design.md)；模型、提醒 ID 和窗口骨架以该主文档为准。

## 数据一致性

TaskService 统一处理新增、改名、完成、撤销、加入某天和移除当日计划。一次操作在同一 ModelContext 中写入实体变化与 TaskEvent，再显式 save；失败时回滚持久化上下文，同时保留 UI 编辑缓冲供重试。

WorkDay 以 UUID 标识，同时维护本地日期和时区；应用服务保证同一工作日期不重复创建。DailyPlanItem 以独立 UUID 关联任务和日期，服务层禁止同一天重复加入同一任务。不能只依赖当前视图是否已有一行判断唯一性。

任务当前状态与历史计划快照分开。TaskEvent 记录修改前后值和绝对时间，历史展示按归属日期截止时间计算。跨午夜若 App 未运行，下次启动补齐截止快照，不能把补齐时的当前状态写成昨日状态。

数据库从第一版建立 SchemaVersion；设计阶段仍可调整字段，发布后必须编写并验证迁移。JSON 导出包含所有实体、关系 ID 和版本，不使用运行中的 SQLite 文件直接复制替代一致性备份。

## 编辑和生命周期

文本编辑在内存缓冲，短时间防抖落盘；任务状态操作立即提交。中文输入法组词阶段不要触发回车提交和意外焦点跳转。菜单栏和主窗口共享 store；业务操作经同一应用服务串行协调。

正常关闭窗口与退出 App 分开：前者保留菜单栏，后者提交待保存内容后结束。保存状态反映真实结果，不用固定计时器伪装成功。崩溃和强制退出前未提交缓冲仍有风险，需要明确测量并考虑恢复草稿。

## 提醒协调

ReminderCoordinator 将用户规则变成有限窗口内的系统通知请求；请求 ID 使用日期、提醒类型和规则版本生成，重复协调应得到相同结果。

协调触发：设置改变、应用启动、唤醒、日期改变。先读取已排期请求，再取消失效项并补充缺失项。通知授权状态单独读取；权限被撤销时不把未排期显示为“提醒已开启”。

工作周与单日例外同时存在时，单日例外优先。时区改变后重建未来请求，旧通知去重；过期提醒汇总一次。具体可排期数量和系统交付限制在真实 .app 上验证。

## AI 边界

LLMProvider 是本项目协议，不依赖未来系统版本的同名抽象。输入使用不含 SwiftData 活实体的值类型快照：来源 ID、修订号、文本、日期范围；返回可校验的草稿及来源引用。

在后台异步执行网络或模型调用，主线程只更新状态。一次生成有 requestID；取消或新请求后，旧结果不能覆盖新草稿。返回后校验来源 ID 均在输入范围内，并比较来源修订号；变化时标记过期。

先实现规则型 MockProvider 验证界面；真实 Provider 接入时记录延迟与错误类别，不记录工作正文或密钥。云端请求范围必须可见，个人日记默认排除；不自动故障转移到另一服务。

## 验收重点

1. 任务状态、事件与保存失败回滚；多窗口修改一致。
2. 历史快照、跨日未运行、周五到周一、调休和时区变化。
3. 提醒请求幂等、旧请求撤销、拒绝权限和点击跳转。
4. 中文输入法、键盘新增、编辑焦点和撤销。
5. AI 取消后迟到响应、来源无效/过期、采纳不覆盖事实。
6. JSON 导出导入往返、关系完整、重复 ID 与迁移。

核心纯逻辑优先单元测试，持久化使用临时 store 做集成测试；少量 UI 测试覆盖新增→完成→重启保留。设计稿只做交互评审，不替代以上验证。
