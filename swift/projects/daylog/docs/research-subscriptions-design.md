# 主题订阅：每日调研的产品与实现设计

2026-09-19 · 提案 v1，尚未实现或启用。延续 C / Graphite Studio。先确认界面和工作流，再接入工具与调度；本次不修改应用、系统后台项或已有定时任务。

## 1. 产品定位

把外部信息变成每天可阅读、可追溯、可采取行动的主题简报。DayLog 的主线仍是“计划 → 做事 → 记录 → 回顾”；主题订阅在这条主线旁提供输入。

推荐默认是每天 09:00 开始、3–5 分钟阅读、最近 24 小时重要变化。主题“LLM 推理与本地部署”仅用于看稿，不代表用户已订阅。阅读篇幅尚待用户反馈；09:00 是开始调研时间，不承诺此时已经完成。

三类内容保持清楚：TODO 是承诺要做的事；工作记录是已经发生的进展；调研简报是外部资料和模型分析。生成一篇简报不自动新增 TODO、不算完成任务，也不自动写入工作记录。

## 2. UI：在现有产品中的位置

| 页面 | 增量 | 保留的边界 |
| --- | --- | --- |
| 今天 | 待办下方、工作记录上方出现一条“今日简报 · 1 份待阅”；可显示主题、阅读量与状态 | 不挤占重点与任务；没有订阅时完全隐藏；多份结果合并为入口 |
| 左侧导航 | 新增“调研”，小圆点只表示有未读结果 | 不用任务完成数表示调研数量 |
| 调研 | 左侧主题及最近各期，右侧阅读与处理；主题头部提供暂停、试跑、编辑 | 不做通用聊天、复杂工作流画布或代理控制台 |
| 订阅编辑 | 主题与来源 → 时间与交付 → 确认与试跑 | 运行条件和下一次时间可见，高级预算折叠 |
| 今日工作记录 | 用户明确采纳后出现一段可编辑摘记，保留“来自主题简报”与引用 | 以采纳当天归属记录，不改写简报生成日的历史 |
| 今日任务 | 用户将一条行动建议转为待办，先编辑标题再确认 | 不自动完成，重复点击不重复创建 |
| 日级回顾 | 默认仍只总结自己的工作事实 | 自动简报和原样采纳的外部摘记不当作已完成工作；用户追加的进展可以进入回顾 |
| 设置 | 模型与工具连接、运行设备与后台状态 | 早晚提醒继续服务工作日记；调研时间在订阅里配置 |
| 菜单栏 | 一条“调研 · 1 份待阅”，点击进入对应简报 | 不在小面板塞整篇报告 |

视觉继续用窄导航、可调分栏、中性表面、细分隔线与铜色重点。常态只显示主题、下次执行和待阅状态。执行细节收进“本次运行”，无需让普通用户理解 MCP、cron 或 token。

### 订阅编辑的三个步骤

1. **主题与来源**：名称、关注问题、排除项；选择公开网页、官方发布、RSS 或已连接工具。默认公开资料；指定站点是偏好还是严格白名单须明确区分。不要自动把已有业务工具全加入。
2. **时间与交付**：每天 / 工作日 / 自定义星期，时间与固定 IANA 时区；工作日可复用现有调休规则。默认每天，避免把用户的“每天”擅自改为工作日。显示运行位置、错过时如何补跑、仅新内容时通知。可选精简简报或深入报告。
3. **确认与试跑**：列出发送内容、实际可用的工具、上限和下一次开始时间。试跑是一次真实受限运行，成功不等于启用日程；可以“只保存配置”或“保存并启用”。缺少检索工具时阻止启用并直达连接设置。

编辑订阅沿用上一轮草稿约定：切页保留、底栏列出待保存输入、离开或退出可定位。保存配置和启用日程是两个动作；Cmd+S 不应悄悄启用后台能力。运行中编辑规则，下次生效，本次冻结旧配置并显示版本。

### 简报阅读结构

- 主题、期次、实际检索截止时间、时间范围、覆盖状态和预计阅读时间。
- “今天值得关注”：0–3 个变化，每条包含事实、为何相关、来源编号；背景信息与本期新增分开。
- “对你意味着什么”：标为分析或推断，不冒充来源事实。
- “可采取的下一步”：建议默认不生成任务；选择后进入可编辑预览。
- 来源抽屉：标题、站点、发布日期/更新时间/抓取时间、原文地址、支持的具体结论；未知日期明确标注。引用链接由检索器返回并校验，不由模型凭空编写。
- “记入工作记录”：选择结论 → 编辑摘记 → 确认；不默认粘贴整篇文章。查看、已读、采纳、转任务相互独立。

折叠和 Markdown 阅读复用现有组件；来源链接用独立原生按钮安全打开已校验的 HTTP(S) 地址，避免依赖当前禁用链接的通用 MarkdownText。

## 3. 每天怎样使用

```mermaid
flowchart LR
    A[创建主题与选定来源] --> B[确认时间与运行条件]
    B --> C[试跑并检查样例]
    C --> D[明确启用订阅]
    D --> E[到期检索与阅读原文]
    E --> F[按日期和内容去重]
    F --> G[带引用的简报 / 无重要更新 / 失败]
    G --> H[今日待阅与可选通知]
    H --> I[阅读并标记已读]
    I --> J[选择摘记或行动建议]
    J --> K[确认后进入日记或 TODO]
```

普通一天：09:00 开始 → 09:04 简报就绪 → 今日页出现待阅入口 → 用户阅读 → 把值得验证的想法变成任务 → 实际验证后记录进展 → 晚上回顾自己的工作。

无更新的一天：保存一次“未发现重要更新”的运行记录，显示已检查的范围；默认不通知、不生成空泛长文。“无更新”只在预期来源覆盖达标时成立，不能掩盖搜索失败。

## 4. 状态与异常要先设计完整

| 状态 | 用户看到 | 可操作与处理 |
| --- | --- | --- |
| 未配置 | “连接检索工具后可开始” | 保存配置、配置工具；不只检查 LLM Key |
| 等待 | “明天 09:00 · Asia/Shanghai 开始” | 立即试跑、编辑、暂停 |
| 运行中 | 检索来源 → 阅读原文 → 整理与核验 | 显示已处理数量与取消；不伪造精确完成百分比 |
| 就绪 | “待阅 · 检索截至 09:04” | 阅读、已读、摘记、转待办 |
| 无重要更新 | 时间范围、实际检查来源 | 查看本次运行、扩大范围后手动重跑 |
| 部分成功 | “仅覆盖 4/6 个可用来源”并列失败部分 | 看带警示的结果、重试失败来源；不标完整覆盖 |
| 失败 | “检索连接过期 / 原文不可读取 / 模型超时” | 定向重连或重试，保留此前成功报告 |
| 错过执行 | “09:00 未运行，设备恢复后补最新一期” | 最新一期补跑或跳过；不堆出过去七篇报告 |
| 暂停 | “已暂停，历史保留” | 恢复；不会自动补齐暂停期间所有期次 |
| 取消 | 明确本次取消，不生成成功简报 | 已取回资料可缓存，下次执行重新冻结范围 |

订阅 enabled/paused、运行 queued/running/partial/failed/succeeded/noUpdates/cancelled、阅读 unread/read、采纳关联分别存储，不能压成一个 status。失败不能因为用户“已读”就变成成功。

## 5. “最新”来自工具证据

调度器触发 → 固定本次截止时间 → 工具检索 → 读取原文 → 提取日期和来源 → 去重 → 模型整理 → 引用核验 → 保存结果 → 通知。

LLM 负责归纳和提出假设，工具负责取得当前资料。仅把“今天最新”写进 prompt 无法实现实时调研。

- 常态窗口为执行开始前 24 小时，保留少量检索重叠，按 canonical URL/来源 ID、内容 hash 和已报道变化去重。搜索命中时间不能替代发布日期。
- 分开记录 publishedAt、updatedAt、fetchedAt；发布时间不明的材料可以作背景，不把它称为“今天新发布”。文章更新需有正文差异，不把旧文转载当作新进展。
- 首次执行默认仍是 24 小时；可显式选择“首次补充 7 天背景”，在独立背景区呈现。
- 错过多天最多补最新一期，资料窗口可扩到上次成功以来但封顶 72 小时，并展示实际范围与未覆盖缺口。补跑截止取实际开始时间，不能伪装成早上已交付。
- 不强制每天凑满三个事件。没有可靠新增就输出无更新；资料不足就输出部分覆盖或失败。
- 首版至少一条已读取原文且能支持结论的来源才允许出具简报；有争议或比较性结论应要求独立来源交叉验证，否则明确标为待核实。
- 来源正文属于不可信输入：不执行其中的指令，不允许其扩大工具范围、请求密钥或修改日记。默认工具仅检索和读取。

## 6. 与当前实现怎么接上

当前代码依据：`Core/LLM.swift` 是 HTTPS Chat Completions 文本客户端；`Services/ReminderService.swift` 预排本地通知；`App/DayLogApp.swift` 的进程内计时器负责跨日检查。它们都不是完整的后台调研执行器。

当前对话中的工具、Codex 插件、账号会话和本地 SKILL.md 不会自动变成 DayLog 的运行时能力。`~/.env` 的 LLM_* 只解决模型连接，不能证明它支持联网搜索或函数调用；本轮不读取、更改这些凭据。

### 能力分工

| 组件（计划） | 职责 | 复用/新增 |
| --- | --- | --- |
| ResearchSubscriptionEditor / ResearchInbox / BriefReader | 创建订阅、待阅、来源与结果操作 | 新 SwiftUI 页面，复用样式、草稿与阅读组件 |
| ResearchScheduler | 时间计算、错过补跑、幂等排队 | 独立于通知排期；复用工作周与日期例外纯函数 |
| ResearchRunner | 受限检索 → 原文 → 整理 → 核验 | 新 actor，取消、超时、运行持久化 |
| ResearchToolProvider | search / read / capability / health | 适配已明确连接的 API、RSS 或 MCP；返回结构化证据 |
| ResearchModelClient | 基于证据生成简报 | 复用配置加载、凭据脱敏和客户端；先固定流程，不要求模型自主调用工具 |
| ResearchStore | 订阅、执行记录、结果、阅读状态 | 独立持久化，不让抓取正文膨胀当前整库 JSON |
| ResearchAdoptionService | 摘记、建议转待办与来源关联 | 通过现有 AppStore.commit 接受，显式确认和去重 |

工具接入分级：先公开检索/原文读取及 RSS；再接已认证的 MCP 或结构化只读适配器。调用已有 CLI/skill 需要明确参数、凭据来源、超时与输出契约；首版不执行任意 shell 或任意 SKILL.md。业务 SQL、内部文档等不作为默认来源，须单独指定范围和传输边界。

每次执行冻结订阅 revision、provider IDs、提示模板版本、时间范围及预算。初始预算建议：每次最多 3 次搜索、8 篇原文、2 次模型请求、总计 5 分钟，同一设备默认一次只运行一个主题；属于可调实现默认值，不是已测吞吐或费用承诺。显示实际 token/费用仅在后端确实返回相关计量时成立。

### 定时方案与产品承诺

| 阶段 | 调度方式 | UI 必须说明 |
| --- | --- | --- |
| 交互和内容验证 | 手动试跑 + 模拟执行状态 | 不创建真实日程 |
| 首个可用版本 | App 进程内调度；关窗后菜单栏进程仍在，启动/唤醒做 due 扫描 | “DayLog 运行且设备可用时执行；退出后暂停，恢复后补最新一期” |
| 后台增强 | 用 SMAppService 注册独立 LaunchAgent，系统定时唤起检查 due 工作；不只依赖 UI Timer | “后台已允许 / 等待系统允许 / 已关闭”；App 退出仍可执行，但需要用户登录、机器和网络可用 |
| 真正不依赖 Mac | 常在线服务器调度、独立凭据与结果同步 | 新增云端信任和运行位置选择；不默认纳入本地优先版本 |

Apple 文档提供 SMAppService 管理 LoginItems/LaunchAgents/LaunchDaemons；launchd 的日历任务不能作为关机时执行或准时唤醒设备的保证。产品层必须自行记录遗漏并补跑。参考 [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice) 与 [Scheduling Timed Jobs](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/ScheduledJobs.html)；后者是归档文档，实际后台、锁屏和睡眠行为仍需目标 macOS 真机验收。

如果需求是“每天开始工作时一定已有简报”，应把提前量和常在线执行环境列为验收条件；本机按 09:00 触发不能承诺 09:00 就绪。

### 数据与并发约束

计划实体：ResearchSubscription（问题、sources、schedule、timeZoneID、enabled、revision）、ResearchRun（occurrenceID、冻结配置、实际范围、状态、错误与计量）、ResearchBrief（版本、结论、建议、readAt）、SourceEvidence（日期、URL、摘录、hash）、AdoptionReference（briefID、blockID、entryID/taskID）。

当前 LocalStore 用一条 WorkspaceDocument 保存完整 Workspace。**不能让后台进程和 App 各加载一份，再独立覆写同一文档**，否则较旧快照会覆盖日记。建议：ResearchStore 与 Workspace 分离；进程内版本由 App 中单个服务写 ResearchStore，后台版本则切换为 helper 单写，App 通过 XPC 命令编辑订阅、标记已读。调研 helper 始终不直接写日记数据库。

结果落盘成功后才通知；系统通知失败不丢结果。自动运行的幂等键按 subscriptionID + 本地逻辑期次，持久化租约防止双运行；规则编辑只重排未开始期次。用户手动重跑形成新版本，失败重试沿用 occurrenceID，防止一次期次发多条通知。系统/时区变更重新计算 nextRun；夏令时重复小时只跑一次，不存在的时间顺延到当天首个有效时刻，保留原计划时间。

采纳时由 App 一次事务写入业务对象及 provenance/去重键；重复操作返回已有关联。ResearchStore 中的“已采纳”是可修复投影，不作为唯一真相，避免跨库一半成功时重复记日记。模型产生的“建议”永不自动调用 addTask。

工作空间需做明确 schema v2 迁移，新增来源关联和外部摘记类别/标识，并更新回顾过滤；v1 备份导入默认无订阅，旧版拒绝 v2，不能靠 Codable 静默忽略字段。新的完整备份在一致的逻辑 revision 边界包含订阅、简报、来源元数据和关联；原文缓存可排除且说明。恢复前暂停 runner 并校验所有引用，恢复后订阅保持暂停，用户确认连接后再启用。凭据永不导出。

## 7. 实施顺序与验收

1. **当前设计轮**：交互稿确认入口、篇幅、来源展示、采纳预览与异常状态；不连接调度。
2. **内容闭环**：单主题手动调研，真实检索/阅读/引用，明确无更新与失败，结果落盘，摘记和任务采纳；先证明“值得每天读”。
3. **应用内定时**：每天/工作日、固定时区、补跑、暂停、取消、只通知新增；不注册后台 helper。
4. **后台运行**：单写 ResearchStore、XPC、SMAppService、权限状态、锁屏/睡眠/重启/退出的实机矩阵。

验收必须覆盖：无新信息不捏造；旧文转载不算新增；失效链接不算读取成功；部分源失败不显示完整成功；私人日记不进入请求；取消后的迟到响应不覆盖；重试不重复通知或新增任务；订阅草稿切页保留；断电/重启不把 working 永久挂住；正常日记编辑与后台结果同时保存互不覆盖；v1/v2 备份迁移和恢复后暂停；时区与 DST；单次和全天预算。

## 8. 本轮评审建议

推荐冻结三个决定：独立“调研”入口但今日页只放轻量待阅条；默认精简且有证据的简报；所有进入日记/TODO 的动作经过明确预览与确认。是否必须支持 App 退出后运行，可以在内容闭环验证后决定，不影响本轮页面结构。

交互稿中的来源、结果和执行时间均为演示，未做真实主题调研。查看稿件不会执行模型请求、安装后台项或启动定时任务。
